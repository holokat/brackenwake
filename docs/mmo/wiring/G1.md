# G1 wiring: the dev bench

Files owned: `src/game/dev.js`, `src/game/win_dev.js`, `src/game/win_dev.test.mjs`
and this note. Nothing else was touched. `main.js`, `windows.js`, `monsters.js`
and everything under `src/mmo/` are read only to G1, so every one-line change
this bench needs from another file is written out below for its owner to apply.

`win_dev.js` exports `panel` (and a default export of the same object) matching
the panel contract in `07-RUNTIME-CONTRACT.md`:

```js
panel = { id: 'dev', title: 'Dev bench', key: 'f2', build, open, tick }
```

---

## 1. The create call and the register

`main.js` already builds `dev`. One import and one register:

```js
import { panel as devPanel } from './win_dev.js';

// ...
const dev = createDev({ sc, camera, player, hud, runtime, state });   // unchanged

for (const p of [characterPanel, bagPanel, skillsPanel, abilitiesPanel,
                 talkPanel, tradePanel, craftingPanel, mapPanel, settingsPanel,
                 devPanel]) windows.register(p);
```

`F1` and the backquote still toggle fly through `onHotkeys`, untouched. `F2` is
read by `windows.update` like every other panel key, so no hotkey code changes.

The panel builds itself on first open, so registering it costs nothing at boot.

## 2. The ctx fields the bench needs

`ctx` is the one object `createWindows(root, input, ctx)` holds. It carries
`character, actor, inventory, state, hud, audio, floaters, runtime, player,
windows, recompute, applySettings, newCharacter, now, station, progression`
today. The bench needs ten more, all of them things `main.js` already has in
scope by the time `ctx` is built or shortly after:

| field | what it is used for | when it exists in main.js |
| --- | --- | --- |
| `ctx.sc` | day clock, `renderer.info` for the readout | before `ctx` |
| `ctx.camera` | `camera.snap` and `camera.yaw` on a teleport | before `ctx` |
| `ctx.combat` | `kill`, `heal`, `hurt`, `forget` | before `ctx` |
| `ctx.monsters` | `actors()`, `count`, `rescan`, `spawnAt` | before `ctx` |
| `ctx.loot` | reserved: a future "drop a sack here" row | before `ctx` |
| `ctx.targeting` | `current` for Kill target, `lastGround` for spawn at the cursor | after `ctx` |
| `ctx.abilities` | `cooldowns`, `applyPassives` | after `ctx` |
| `ctx.dev` | fly toggle and the debug switches | after `ctx` |
| `ctx.debug` | the same object as `dev.debug`, for whoever draws overlays | after `ctx` |
| `ctx.effects` | reserved: a future "play this effect" row | after `ctx` |

Five of them (`sc`, `camera`, `combat`, `monsters`, `loot`) go into the object
literal; the rest are assigned after their module is built, exactly the way
`ctx.windows` and `ctx.progression` already are:

```js
const ctx = {
  character, actor, inventory, state, hud, audio, floaters, runtime, player,
  sc, camera, combat, monsters, loot,          // <- added
  windows: null,
  // ... everything already there
};
// ... after the modules that come later are built:
ctx.targeting = targeting;
ctx.abilities = abilities;
ctx.effects = effects;
ctx.dev = dev;
ctx.debug = dev.debug;        // one object, so the panel and the drawers agree
```

`ctx.dev` and `ctx.debug` have to be set after `const dev = createDev(...)`,
which is the last line before `applySettings`. Everything else can go earlier.

**Nothing is required.** Every action checks for what it needs and, when it is
not there, says in words what is not wired and changes nothing. The tests drive
both directions: `bench.teleport` with no `player.teleport` makes zero calls and
returns `the player cannot be moved from here: no teleport is wired.`

## 3. The one-liners other files need

Each of these is in somebody else's file. Until it lands, the bench says so out
loud rather than pretending; the wording it uses is quoted underneath.

### 3.1 `src/game/combat.js`: god mode (owner: W2 / Fable)

`actor.godMode` is written by the bench and read by nothing yet. Three sites
take health off an actor, and all of poison, bleed and falling already go
through the first of them:

```js
// in hurt(), after the `if (!alive(actor) || n <= 0) return 0;` line
if (actor.godMode) return 0;

// in landSwing(), immediately after `const res = ...`
if (defender.godMode) { res.damage = 0; res.killed = false; res.numbers = res.numbers.filter((n) => n.kind !== 'damage'); }

// in landSpell(), immediately after `const res = ...`
if (defender.godMode) { res.damage = 0; res.killed = false; res.numbers = res.numbers.filter((n) => n.kind !== 'damage'); }
```

The bench does not take this on faith. Turning god mode on runs a real
`combat.hurt(actor, 1)` through the real resolver and heals back whatever it
took, so the line the player sees is measured:

> god mode on, but a test blow still took 1 off. combat.js does not read
> actor.godMode yet; docs/mmo/wiring/G1.md has the lines.

and once the three lines land it says instead:

> god mode on. A test blow took nothing off you.

Both branches are covered by `win_dev.test.mjs`.

### 3.2 `src/game/monsters.js`: spawn one where I say (owner: W2 / G3)

`createMonsters` has a private `spawn(rec)` that builds the model, the actor and
the record and puts it in `live`. It needs one line on the returned object, next
to `rescan`:

```js
/** One monster, here, now. The dev bench and the dungeon spawner both want this. */
spawnAt(id, x, z) {
  return spawn({ id, x, z, key: `at-${id}-${(stats.spawned + 1).toString(36)}-${Math.random().toString(36).slice(2, 6)}`, groupKey: null });
},
```

The key has to be unique and must not collide with a chunk slot key, or the
streamer will despawn it on the next sweep. A spawn made this way is a real
monster: it has a body, an actor, aggro, loot and a death, because it went
through the same `spawn` the streamer uses.

Until it lands the bench says:

> no Wolf appeared: src/game/monsters.js has no spawnAt(id, x, z) yet.
> docs/mmo/wiring/G1.md has the one line it needs.

### 3.3 `src/game/scene.js`: the time of day slider (owner: V1 / Fable)

`dayFactorAt(nowMs)` is pure and `sc.dayFactor(nowMs)` calls it with no offset,
so nothing can move the sun. Two lines:

```js
let clockOffset = 0;
/** Shift the day. The dev bench's time slider; nothing else writes it. */
function setClockOffset(ms) { clockOffset = Number.isFinite(ms) ? ms : 0; return clockOffset; }
// and in the returned object:
dayFactor(nowMs) { return dayFactorAt(nowMs + clockOffset); },
setClockOffset,
get clockOffset() { return clockOffset; },
```

`main.js` reads the day once a frame through `sc.dayFactor(now)` and hands it to
`runtime.update`, `sc.setDay` and the night flag, so one offset moves the sky,
the fog, the lights, the fauna and the monster spawn table together.

`win_dev.js` computes the offset itself (`clockOffsetFor`, tested against
`dayFactorAt` to 1e-9: noon reads 1.0, midnight reads 0.0) and only hands the
number over. Until `setClockOffset` exists:

> the sky has no clock to set: scene.js needs setClockOffset(ms). It is still 14:52.

### 3.4 The two overlay switches (owners: V3 for chunks, W2 for colliders)

`dev.js` owns `dev.debug = { chunks: false, colliders: false }`, and
`DEBUG_FLAGS` is the whole list. The bench flips them through `dev.setDebug`,
which refuses a name nobody declared. Nothing draws them yet:

- `chunks`: `src/world/chunks.js` should draw a wireframe box or a line grid on
  each loaded chunk while `debug.chunks` is true. It has the chunk records and
  their bounds; nothing else does.
- `colliders`: whoever owns the collision shapes (site flat discs, dungeon
  walls, monster radii) should draw them while `debug.colliders` is true.

Both read the same object main.js hands over as `ctx.debug`. The bench's line
names the reader, so a switch that does nothing says who has to answer it.

## 4. What `dev.js` changed, and what it did not

`F1` fly is byte for byte the behaviour it had: `camera.setMode('fly')`, the
player hidden and unsimulated, the badge, the lens on `state.dev`, and on the
way out the landing on the ground under the camera and the tool handed back.
The toast now also mentions F2.

Two things were added:

1. **`character.settings.dev` is written on every switch**, which is what
   `08-POLISH-CONTRACT.md` asks for by name. `state.dev` is unchanged and still
   is not saved: it is the live lens the tool row and the market read. The
   document holds the intent, `state.save()` carries it, and `applySettings` in
   main.js already puts the mode back at the next boot with its existing line:

   ```js
   if (typeof s.dev === 'boolean' && dev.on !== s.dev) dev.toggle();
   ```

   There is no loop: `persist` is quiet when the value has not changed.

2. **`dev.debug` and `dev.setDebug(key, value)`**, section 3.4.

### A note for whoever owns state.js

`state.js` `DEFAULT_SETTINGS` has no `dev` key (it also carries `music: true`
where `win_settings.SETTINGS` has `music: 0.5`, a range). In the running game
this does not bite, because `startGame` calls `normaliseSettings(character.settings)`
before anything reads them and `win_settings` fills in every key. A blank
document straight out of `createState`, though, has `settings.dev === undefined`
until the first switch. `win_dev.test.mjs` records that as a measured fact
rather than papering over it. Worth reconciling the two tables one day; it is
not G1's file.

## 5. What the panel does, and what it goes through

Nothing here has a second code path. That is the whole design.

| row | what the button calls |
| --- | --- |
| Gold +100 / +1,000 / +10,000 | `state.earn(n)`, then reads `state.coins` back |
| Skills all to 100 / restore | writes `character.skills` **in place**, then `ctx.recompute(actor)` and `state.touch('skills')` |
| Stats all to 100 / restore | same, on `character.stats` |
| Learn every ability | raises only the skills and stats that gate one, then counts with `abilities.unlockedFor`. The bar is never written |
| Reset cooldowns | deletes the keys off `abilities.cooldowns`, the object the runtime reads |
| God mode | `actor.godMode`, then the probe in 3.1 |
| Heal and refill | `combat.heal(actor, missing)`, then mana and stamina to their maxima |
| Give item | `items.makeItem` -> `affixes.withAffixes` (above common) -> `inventory.add` -> `inventory.identify({ pack: i }, { scroll: true })` |
| Full sets | the same give, once per base, counting what went in and what did not |
| Teleport | `player.teleport`, `camera.snap`, `state.setPos`, `monsters.rescan`, `combat.forget`, in that order |
| Enter | the teleport, then `runtime.enterDungeon(site)`; main.js's `onDungeonState` does the rest and says where you are, so the bench stays quiet |
| Deeper / Out | `runtime.dungeonGo('down' / 'up')` |
| Go to x, z | the same five as a teleport |
| Spawn | `monsters.spawnAt(id, x, z)`, six metres ahead or at `targeting.lastGround` |
| Kill target | `combat.kill(targeting.current, actor)`, so the sack drops and the dead list is written |
| Kill all within 30 m | `combat.kill` per live actor inside the radius |
| Clear aggro | `ai.target = null`, `ai.state = 'idle'`, `combat.forget(a)`, skipping corpses |
| Time of day | `sc.setClockOffset(ms)` |
| Fly | `dev.toggle()`, the same thing F1 does |
| Chunk borders / colliders | `dev.setDebug(key, on)` |

**Every one of them says what it did.** A give names the item and the slot, and
whether it is known or still a mystery. A refusal names what did not happen and
why. A teleport names the place and how far off it was. The readout along the
bottom counts fps, monsters alive, chunks loaded, draw calls, where you are and
how deep, and reports `null` in words for anything that is not wired rather
than a zero it made up.

## 6. `window.__bw`

`__bw` already carries `dev`. Add the bench so the console can drive it without
opening the window, and the panel so a test can rebuild it:

```js
window.__bw = {
  // ...everything already there
  devPanel,                              // the panel object
  get devBench() { return devPanel._bench || null; },   // built on first open
};
```

`_bench` is `createBench(ctx)` and is set by `panel.build`, so it is null until
F2 has been pressed once. A console that wants it before then can call
`createBench(__bw.windows.ctx)` itself; it is the same function the panel calls,
with the same ctx.

Beware the module-instance trap: a dynamic `import('./win_dev.js')` in the
browser console gets a different module instance with its own `saved` sheets, so
a restore driven that way would put back a sheet nobody kept. Go through
`__bw.devBench`.

## 7. What is measured, and what is not

`node src/game/win_dev.test.mjs`: **152 checks, 152 green.** The suite runs the
bench against the real `state.js`, `actor.js`, `inventory.js` and `combat.js`;
only `player`, `camera`, `runtime`, `monsters`, `targeting` and `sc` are
recorders, because those need THREE or a canvas.

Measured:

- a rare plate breastplate arrives in the pack identified, with the two affixes
  rare rolls, none of them vague, and `material: 'iron'` on the record
- an epic longsword given unidentified stays unidentified, with its three
  affixes already rolled from the seed
- a full 20 slot pack refuses a give: the pack is byte for byte what it was, no
  slot became a breastplate, and the refusal says the pack is full
- a plate set into a pack with three slots left puts in 3 and reports 5 refused
- a teleport calls exactly `player.teleport, camera.snap, state.setPos,
  monsters.rescan, combat.forget`, in that order, with the document moved to
  where the feet are and the camera turned to face the place
- skills restore returns the exact sheet, key for key, fractions included
  (41.5 and 63.25 came back as 41.5 and 63.25), written into the same object so
  `actor.baseSkills === character.skills` still holds
- `learnAllAbilities` takes a blank sheet from 6 unlocked abilities to all 78,
  and nothing any ability asks for is above 100 (the highest is 95)
- the site list groups town, hamlet, dungeon, cave, ruin, shrine, camp and then
  any kind `KIND_ORDER` has never heard of, each group sorted by a measured
  distance
- `sitesNear(field, 0, 0, 6000)` against the real world field returns **119
  sites**, all seven kinds present (34 hamlets, 22 ruins, 17 shrines, 16
  dungeons, 13 towns, 11 camps, 6 caves), in 5.5 ms cold and 0.1 ms warm. That
  is an open-time cost, not a per frame one. The list keeps the nearest 12 of
  each kind and the group header says so when it held any back
- the monster search finds all three wolves by the substring "wolf", lowest
  tier first, case insensitively
- `clockOffsetFor` lands on the phase it was asked for to 1e-9, and noon reads
  `dayFactorAt` 1.0 while midnight reads 0.0
- the god mode probe reports "not honoured" against today's combat.js and
  "honoured" against a resolver that reads the flag
- every unwired branch: no teleport, no spawnAt, no setClockOffset, no ability
  runtime, no dev module. Each makes zero calls and returns a sentence.

Not measured, and honestly so:

- **Nothing was run in a browser.** No button was clicked, no CSS was seen. The
  DOM half of `win_dev.js` is `panel.build`, which is buttons wired to bench
  calls and nothing else; the bench under them is the tested part. Fable's
  browser pass is what proves the layout.
- **`monsters.spawnAt` does not exist yet**, so no monster has actually been
  spawned by this bench. The call and the failure wording are tested; the spawn
  is not.
- **`sc.setClockOffset` does not exist yet**, so the sun has not been moved. The
  arithmetic is tested against `dayFactorAt`; the sky is not.
- **God mode is not yet honoured by combat.js.** The bench says so.
- The `chunks` and `colliders` flags are written and nothing reads them, which
  is the point of section 3.4, and the panel's own line says who must.
- `npm test` has two red suites that are not G1's and were green on a clean
  tree: `src/game/audio.test.mjs` and `src/game/trade_net.test.mjs`, both from
  another agent's work in flight while this was written.
