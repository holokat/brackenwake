# W3 wiring: inventory, the window manager, four panels, creation

Files owned: `src/game/inventory.js`, `src/game/windows.js`,
`src/game/win_character.js`, `src/game/win_bag.js`, `src/game/win_skills.js`,
`src/game/win_abilities.js`, `src/game/creation.js`, their `*.test.mjs`, and
this note. Nothing in `src/mmo/` was touched.

## The create calls, in order

```js
import { createInventory } from './inventory.js';
import { createWindows } from './windows.js';
import { createCreation } from './creation.js';
import { panel as characterPanel } from './win_character.js';
import { panel as bagPanel } from './win_bag.js';
import { panel as skillsPanel } from './win_skills.js';
import { panel as abilitiesPanel } from './win_abilities.js';
// W5's five
import { panel as talkPanel } from './win_talk.js';
import { panel as tradePanel } from './win_trade.js';
import { panel as craftingPanel } from './win_crafting.js';
import { panel as mapPanel } from './win_map.js';
import { panel as settingsPanel } from './win_settings.js';

// 1. No save, or "New character" in settings: creation first, the game after.
if (!character) {
  createCreation(hudRoot, {
    sc,                       // the scene, for the darkened backdrop and the turning rig
    buildCharacter,           // from player.js
    onDone: (character, plan) => startGame(character, plan),
  });
  return;                     // createCreation removes itself before onDone fires
}

// 2. With a character in hand.
const inventory = createInventory({
  character,                  // the v2 document from state.js (W1)
  actor: playerActor,         // from actor.js (W1)
  recompute,                  // actor.js's recompute; called after every change
  onChange: (character, what) => { state.save(); hud.refresh?.(); },
  hud, audio, floaters,
  onSell: (item, where) => vendor ? { price: vendor.offerFor(item) } : { ok: false, reason: 'nobody out here is buying' },
  onDrop: (item, where) => lootDrops.spill(player.pos, [item]),
});

const ctx = {
  character, actor: playerActor, inventory, state, hud, audio, floaters,
  runtime, player, windows: null,      // filled in below if a panel wants it
  onBarChange, onSkillLock, useItem, applySettings,   // see Hooks
};

const windows = createWindows(hudRoot, input, ctx);
ctx.windows = windows;
for (const p of [characterPanel, bagPanel, skillsPanel, abilitiesPanel,
                 talkPanel, tradePanel, craftingPanel, mapPanel, settingsPanel]) {
  windows.register(p);
}
```

**Registration order matters only for the keys.** `register` refuses a second
panel with the same id, and refuses to hand the same key to two panels: the
first registration keeps the key and the second is registered with `key: null`
and a console warning. Registering mine first means C, B, K and A are certainly
mine. Nothing collides today: c, b, k, a, v, m, escape, and Talk and Trade are
opened by code with no key at all.

## Where in the frame

One line, after `hud.update` and before `sc.render`:

```js
windows.update(dt);
```

`update` reads `input.pressed` for every registered key, so it must run inside
the frame and before `input.endFrame()`. It also ticks the open panels, which
is how the character sheet's pools and the bag's weight stay live.

## ctx fields read

| field | read by | what happens without it |
| --- | --- | --- |
| `character` | all four panels | falls back to `inventory.character`; with neither, the panels draw an empty sheet rather than throwing |
| `inventory` | character, bag | the doll and the grid draw, and every click is a no op |
| `actor` | character | AR and resists fall back to inventory.js's own sums of the same gear |
| `hud` | all four | `hud.log(text, kind)` if it exists, else `hud.toast(text, kind)`; nothing said at all if neither |
| `audio` | inventory | `play('pickup' \| 'denied' \| 'sell' \| 'discover')`, all four already in `CUES` |
| `floaters` | inventory | rising `+3 Arrow` and `+27` gold over `actor.pos`; skipped when there is no actor |

`state`, `runtime` and `player` are passed through to W5's panels and are not
read by mine.

## Hooks main.js has to supply

| hook | called by | signature | what it must do |
| --- | --- | --- | --- |
| `onChange(character, what)` | inventory, on every change | `what` is one of `pack`, `equipment`, `gold` | save, and redraw anything of the HUD that shows gear |
| `recompute(actor)` | inventory, on every change, before onChange | actor.js's | sum bonuses, AR, resists, pools |
| `onSell(item, where)` | `inventory.sell` | returns `{ price, count? }` or `{ ok: false, reason }` | the vendor's price. Without it selling refuses out loud and nothing is lost |
| `onDrop(item, where)` | `inventory.drop` | | put a loot bag on the ground (W2) |
| `ctx.onBarChange(bar, slot)` | win_abilities | | tell hud.js's bar to redraw (W4) |
| `ctx.onSkillLock(skillId, lock)` | win_skills | | save; nothing else needs to know |
| `ctx.useItem(item, where)` | win_bag's right click menu | | drink the potion, eat the food, apply the bandage (W4). Without it the menu says so plainly rather than looking broken |

## Events and payloads other agents need

**The drag payload.** `windows.js` exports `DRAG_MIME` (`text/plain`),
`dragSource(el, getPayload)` and `dropTarget(el, onDrop)`. Two payload shapes
travel on it:

- an item address, the same `where` shape `inventory.parseWhere` takes:
  `{ pack: 3 }` or `{ slot: 'mainHand' }`. Drops call
  `inventory.move(from, to)`, so the pack and the doll are one drag space.
- an ability: `{ ability: 'powerStrike' }`.

**For W4.** The real bar in `hud.js` should call
`dropTarget(slotEl, (p) => p.ability && setBarSlot(character, i, p.ability))`
with `setBarSlot` imported from `win_abilities.js`, then `onBarChange`. Until
it does, the abilities window draws its own strip of the same twelve slots and
assigning works there, so the feature is whole on its own.
`win_abilities.js` also exports `BAR_SLOTS` (12), `BAR_KEYS`
(`1234567890-=`), `barOf(character)` and `keyFor(character, slot)`, which reads
`character.settings.bar` so a rebound key shows the binding.

**For W5.** The manager matches 07 exactly, plus four additions W5 panels may
use: `consumes(key)`, `refresh(id)`, `bodyOf(id)`, and the
`attachTip`/`showTip`/`hideTip`/`dragSource`/`dropTarget` helpers exported from
`windows.js`. A panel may declare `keys: ['1', '2']` and those keys are then
reported by `windows.consumes(key)` while it is open; the ability runtime
should skip a key `consumes` claims. WASD, space and the mouse are never
claimed.

## `window.__bw`

Add three: `inventory`, `windows`, `creation`. All three are live objects, not
getters, except that `character` is worth exposing as a getter since W1 replaces
the document on load.

```js
window.__bw = { ...existing, inventory, windows, get character() { return character; } };
```

Useful from the console: `__bw.inventory.add(__bw.THREE ? ... : item)`,
`__bw.windows.open('bag')`, `__bw.windows.openIds`, `__bw.inventory.weight()`.

## Rules the manager keeps

- One window at a time. `PAIRS` is `[['bag', 'character']]` and is the only
  exception; opening anything else closes what is up.
- Escape closes the top window, meaning the most recently opened. With Bag and
  Character both up it takes two presses. With nothing open, Escape opens
  whichever panel registered under the escape key, which is W5's Settings.
- Windows drag by the title bar, cascade so two are never exactly stacked, and
  raise to the front of the layer on any pointerdown.
- The layer is `pointer-events: none` with the windows themselves `auto`, so a
  click beside a window reaches the world.
- The manager runs headless. `createWindows(null, input, ctx)` registers, opens,
  closes, escapes and reads keys with no document at all, which is what
  `windows.test.mjs` drives. Only `build()` is skipped when there is no DOM.

## What was invented, and why

| thing | why | where |
| --- | --- | --- |
| Name rule: 2 to 20 letters, spaces, apostrophes, hyphens, starts with a letter | nothing writes one down and a nameless save is worse | `creation.js` `validateName` |
| Kit fallbacks | `PREFERRED` names the base each kit entry wants; `FALLBACK` names the stand in for any that items.js lacks, and both `STAND_INS` and `MISSING_BASES` are computed at load from what the tables actually hold. As of this pass items.js has a row for all 74, so both lists are empty and every kit lands in full. If a row is ever removed, the fallback takes over and the shortfall is said out loud | `creation.js` |
| Lock cycle order: up, locked, down | 01 names the three states and no order | `win_skills.js` `LOCK_CYCLE` |
| Paper doll layout, six cells then five then the three hands | 03 gives fourteen slots and no arrangement | `win_character.js` `DOLL`, counted by `auditDoll()` |
| Identify roll of 450 ms | 06 says "a short roll animation" | `win_bag.js` `ROLL_MS` |
| Stack size is unlimited | 03 gives no stack cap, so none was invented | `inventory.js` |

Settings defaults are **not** invented here: `creation.js` calls
`defaultSettings()` from W5's `win_settings.js` so the document's first save and
the settings window cannot hold two different tables.

## Load time audits

Three, all of which throw on import rather than shipping a lie:

- `win_character.auditDoll()`: the doll has a cell for every slot in
  `items.SLOTS`, once each, with a label. A fifteenth slot fails here.
- `creation.auditKits()`: every base the openings name has a decision recorded,
  every decision points at a real item base, and no opening would start with
  nothing. A twelfth opening naming a new thing fails here.
- `win_abilities`: twelve keys for twelve slots.

## Things W3 does not do

- **The paladin's holy book and the rogue's second dagger stay in the pack.**
  Nothing displaces anything while a kit is handed over, so a buckler is never
  shouldered out by a book, and `shortfallLine(plan)` names what stayed behind.

- **The model does not wear the kit.** Creation turns the rig from
  `buildCharacter()` and scales it by height. Build, skin, hair and marks are
  written to `character.appearance` and shown nowhere, because `buildCharacter`
  takes no arguments. When W6's rigs land, creation needs one line: pass the
  appearance in.
- **`statLocks` has no consumer.** 07 lists the field and it is written as `{}`,
  but `stats.rollStatGain` takes no lock, so there is nothing to honour a stat
  lock and the skills window offers no control for one. This is recorded rather
  than half built.
- **Dual wielding.** 03 allows a second one handed weapon in the offHand for
  Fencing and Swordsmanship. `items.slotsFor` gives a dagger only `mainHand`,
  so the rogue's second dagger goes to the pack. The rule belongs to the pure
  layer and was not added here.
- **The bag's `use`.** The right click menu offers it and calls
  `ctx.useItem`; nothing consumes a potion yet, and without the hook the menu
  says so.
