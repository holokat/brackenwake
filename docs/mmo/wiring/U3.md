# U3 wiring: one Character page, and the hover that tells you whether the sword is better

Files owned and touched: `src/game/compare.js` (new), `src/game/compare.test.mjs`
(new), `src/game/win_character.js`, `src/game/win_bag.js`,
`src/game/windows.js`, `src/game/ui_theme.js`, their `*.test.mjs`, and this
note. Nothing in `src/mmo/` was touched, and `inventory.js`, `actor.js`,
`main.js`, `hud.js` and `paperdoll.js` were read and not edited.

## The request, and what it turned out to mean

> "Character and Inventory should be in the same HUD view so I can easily swap
> gear and see what it looks like and how it impacts my stats."

The sheet and the pack were two tabs of the codex. Deciding whether a sword was
an improvement was four acts: open the pack, remember the number, double click,
close the pack, open the sheet, read the number. That is not a decision, it is
bookkeeping. So the pack moved into the sheet's right hand column and the
Inventory tab was deleted, and the numbers learned to answer the question
before you commit to it.

## The page

Three columns, in one frame:

| column | what is in it |
| --- | --- |
| left | the name, the title, the character's own line, then **ATTRIBUTES** (5 rows), **COMBAT STATS** (3 pools, armour, attack, defence, dodge, parry, both crits) and **RESISTANCES** (5 rows), then the parchment note |
| centre | the arch with the live rig in it, seven slots down each flank, the motto plate |
| right | the pack: the five filters, the grid of gilded squares, then gold and the load underneath, then the line that counts the slots |

The codex frame went from `min(1180px, 96vw)` to `min(1320px, 96vw)`. At 1180
the pack's grid drops to four squares a row and forty slots become ten rows;
at 1320 it is six across and seven down and the whole page fits the body's
`min(72vh, 760px)` without a scroll on a 900 px screen. Under 1120 px the
three columns stack, which is the same breakpoint the page had before.

**Resistances moved from the right column to the left**, because the right
column is the pack now, and because the user asked for every number that a
piece of gear could move to be in one place that lights up.

## The keys

| key | what happens |
| --- | --- |
| **C** | the codex on Character, plain |
| **B** | the codex on Character, with the pack lit for `FOCUS_SECONDS` (1.6 s) |
| C or B again | closes the codex |
| K, P, V, M | Skills, Abilities, Crafting, Map, unchanged |
| Escape | unchanged |

**C and B are two names for one page, and both toggle it.** Pressing C and then
B closes the codex rather than moving the highlight, which is the one surprise
in the rule and is deliberate: every other key in this game closes what it
opened, and a key that sometimes closes and sometimes refocuses is a key
nobody can predict. `windows.test.mjs` drives that sequence.

## The alias, which is how main.js keeps working

`main.js` is not mine and still does
`for (const p of [characterPanel, bagPanel, ...]) windows.register(p)`. So:

```js
export const CODEX_TABS = [character, skills, abilities, crafting, map];  // five
export const TAB_ALIAS = { bag: 'character', inventory: 'character' };
export const resolveTab = (id) => TAB_ALIAS[id] || id;
```

- `bagPanel` still registers and still carries `key: 'b'`, so B is bound.
- `drawTabs()` walks `CODEX_TABS`, which no longer holds `bag`, so no Inventory
  tab is drawn.
- `open`, `close`, `isOpen`, `toggle`, `raise`, `bodyOf`, `frameOf` and
  `refresh` all resolve the alias, so `windows.open('bag')` and
  `windows.open('inventory')` land on Character.
- `open` puts the name you used into `extra.focus`, which is how the page
  knows B from C.
- The alias only bites **when the page it points at is registered**. An
  embedder that registers the pack and not the sheet gets its pack as a page
  of its own rather than a warning about a panel it never asked for. That
  fallback is measured.

`win_bag.js`'s `panel` is now `{ id, title, key }` and **has no `build`**. The
grid is built by the exported `buildBag(el, ctx, opts)`, which is what
`win_character.js` calls and what `win_bag.test.mjs` drives. A `build` that
nothing would ever call is a lie waiting to be believed.

`main.js`'s boot toast still reads "B bag", which is still true. No edit needed.

## compare.js

Pure, node runnable, no DOM and no THREE.

```js
previewEquip(character, actor, item, slot?) -> { before, after, deltas, changed,
                                                ok, reason, slot, displaced,
                                                worn, verdict }
equippedFor(character, item, hint?)        -> { slot, slots, items, twoHanded }
equippedCard(character, item, hint?)       -> { head, blocks[], slot, twoHanded }
readNumbers(fighter, character)            -> the twenty one numbers
actorFor(character, actor)                 -> the live actor, or a real one
```

**The preview is the real path.** It does not reimplement which slot a ring
goes in, what a two handed weapon does to a shield, or how a plate chest is
halved by a STR that cannot meet it. It clones the document, calls
`createInventory(clone).equip(...)`, then runs `actor.js`'s own `recompute` on
a copy of the actor. Every rule that decides the outcome is the rule the game
uses when you really put the thing on.

**It never touches the world.** `compare.test.mjs` `JSON.stringify`s the
character and the actor, runs four previews, and compares byte for byte. It
also proves the clone is a *different* object, so the byte test cannot pass by
accident.

### The twenty one numbers

The five stats, maxHealth, maxMana, maxStamina, armour, attack, defence, dodge,
parry, critical chance, critical damage, the five resists, carry.

Higher is better for **all** of them, which is why `better` is simply
`delta > 0`. `SHOWN` carries a note saying that if a number is ever added where
lower is better it needs a flag and that sentence stops being true.

**Rounding happens before the difference is taken**, so the `(+n)` a player
reads is the difference between the two numbers in front of them and never a
hidden fraction. Whole numbers round; the three pools are **floored**, because
that is how the sheet has always printed 192.5 health as "192"; chances round
to a tenth of a percentage point; the crit multiplier to a hundredth.

`auditShown()` runs at import and fails if `SHOWN` names a number
`readNumbers` does not produce, or `readNumbers` produces one nothing shows.

### One reader for one number

`sheetOf` in `win_character.js` no longer computes anything itself. It calls
`readNumbers` and formats what comes back, so the plain sheet and the previewed
sheet are the same arithmetic and cannot drift. That is measured directly:
`compare.test.mjs` compares all twenty one of `previewEquip(...).before`
against `sheetOf(...).nums`, with a live actor and without one.

Three consequences of that, all deliberate:

- **`fighterFor` is now `actorFor`.** With no live actor the sheet builds a
  real `playerActor` from a copy of the document instead of the hand rolled
  stand in it used to build. That fills in stamina, the weapon in hand and
  every affix sum exactly as the game would. Every assertion the old
  `fighterFor` had still holds and still runs.
- **The attributes are the EFFECTIVE stats**, not the document's. A worn +2 STR
  ring shows 70, not 68, which is what the fight reads and what the preview has
  to be able to add to.
- **The pools prefer the actor's maxima**, so a +20 health affix shows in the
  health row. Before, the sheet recomputed `derived()` off the document and the
  affix was invisible.

## The hover

Put the cursor on anything in the pack or on the doll and three things happen
at once.

1. The item's own tooltip, as before.
2. A second card **beside** it, headed EQUIPPED, holding what is worn in the
   slot this would take: the glyph, the name in the rarity colour, the slot in
   words ("in your off hand"), and the item's lines. A slot with nothing in it
   says **"nothing worn there"** rather than being left out, because an empty
   block is the answer to "what would I lose". A two handed weapon gets **two**
   blocks, the main hand and the off hand.
3. Every one of the twenty one that would move is redrawn **at its new value**,
   green up or red down, with `(+2)` or `(-18%)` after it, in the sheet's left
   column and in the pack's own load line.

Taking the cursor away puts the plain numbers back. Equipping leaves the new
numbers standing, plain, because they are the truth now. The `dblclick`
handler calls `onLeave` explicitly, so a cursor sitting still over a slot that
has just emptied does not keep a preview alive for an item that has gone.

If the item cannot go on, the card carries the refusal or the penalty **before
you click**: "The Warhammer wants 65 STR and you have 20. You cannot hold it
steady." That is `items.canEquip`'s own sentence, not a second copy of it, and
double clicking says the same thing in the log.

### The preview survives the redraw

The page rebuilds its numbers four times a second. `draw()` writes the plain
numbers into `plain` and then `paint()` decides, per number, whether to show
the plain one or the previewed one. That order is what lets the tick run
underneath a live hover without wiping it, and it is measured: two `tick(0.3)`
calls with the cursor still down leave the green 70 standing.

`bag.draw()` runs **before** `paint()` for the same reason: it writes the plain
carry limit into the line under the grid, and `paint()` is what turns that
number green. The other order would make the load line the one place the
preview did not show.

### `carry` is printed once and lit once

`nums` maps an id to a **list** of elements, not one element, because `carry`
is printed under the pack and would otherwise be the one number that stayed
plain while its twin went green. `buildBag` returns `carryNum` and `carryDelta`
so the sheet can register them. That is why the load line is built out of four
spans rather than one string.

### The cost of a hover

The EQUIPPED card is worked out once, when the cursor arrives, and kept. The
tooltip's getter runs on every `pointermove`, and cloning the document to
decide which slot a ring goes in sixty times a second for an answer that cannot
have changed is work nobody asked for. Measured, on a machine with five other
agents building on it:

| | cost |
| --- | --- |
| one `pointermove` over a filled cell | **57.5 us** |
| one fresh hover (leave, enter, full preview and card) | **222 us** |
| `previewEquip` alone | 150 to 469 us, run to run |
| `equippedCard` alone, which the cache saves per move | **42 us** |

At 60 Hz a `pointermove` is 0.35% of a frame.

## Drag and drop

- pack square to pack square, pack square to a doll slot, doll slot back to the
  pack, ring to ring. All of them are `inventory.move(from, to)`, unchanged.
- **Every path says something.** `inventory.move` speaks for equip, unequip and
  the ring swap. The paths it considers unremarkable, which is the pack to pack
  shuffle, are spoken for by the panel: "longsword goes into slot 7 of the
  pack". A silent drag is indistinguishable from one that failed.
- A drop back onto the slot it came from says nothing and does nothing.
- Dropping onto a doll cell with no inventory in `ctx` says so rather than
  doing nothing.

## The tooltip grew a second card

`windows.js`:

```js
showTip(lines, colour, x, y, compare = null)
attachTip(el, getter, hooks = null)      // hooks: { onEnter, onLeave }
```

Both additions. The getter may now return `{ lines, colour, compare }`; the
old two field shape still works, which is why `win_abilities.js` needed no
edit. `#bw-tip` became a flex row with `.bw-tip-main` and an optional
`.bw-tip-cmp` beside it under a gold rule.

`.bw-up` and `.bw-down` live in `ui_theme.js`, next to the rarity colours, with
`theme.up` and `theme.down` as tokens. One language for better and worse, in
the file that owns the look.

## What was measured

`node run-tests.mjs` per suite, plus these numbers from the suites I own.

- **compare**: 105 checks.
  - A `+2 STR` ring previews **str 68 to 70, delta +2, better**, and nothing
    else moves except carry `+4` (two stones a point) and health `+1` (half a
    point). Every other one of the twenty one is flagged unchanged with a zero
    delta.
  - A plate chest at 60 STR previews armour **0 to 12**, checked three ways:
    against `recompute(playerActor(worn))` run by hand (12), against
    `items.armourOf(plate, stats)` (12), and against the flat number. The same
    chest on 80 STR arms is **24**. The penalty sentence is carried out and not
    swallowed.
  - A greatsword against a kite shield previews **parry 18% to 0%, delta -18,
    better false**, and displaces the longsword and the kite. A plain shield
    carries **no AR** in `items.js`, so the number that falls is parry, not
    armour; put a `+5 AR` line on the shield and the ARMOUR row previews
    **5 to 0, delta -5**, which is the red case the reference sheet shows. Both
    are tested.
  - A warhammer at 20 STR is **refused**, says "wants 65 STR and you have 20",
    and previews nothing at all changing.
  - Four previews leave the character and the actor **byte for byte** where
    they were, `JSON.stringify` compared. `previewActor` leaves the actor it
    was copied from untouched, snapshot compared.
  - All twenty one `before` values equal `sheetOf(...).nums`, with a live actor
    and with none.
  - `equippedFor` across **thirteen** kinds of slot, each finding its own empty
    home; the fourteenth is `ring2`, which is covered by the ring case: bare
    hands take `ring1`, one ring on sends the next to the **empty** `ring2`,
    both full displaces `ring1`. A hint wins when it is one of the item's own
    slots and is ignored when it is not. `slotFor` is checked to equal
    `createInventory(...).chooseSlot(...)` exactly, so it is inventory's logic
    and not a copy.
- **win_character**: 113 checks, 60 of which are the sheet's own arithmetic as
  before. The new 53 build the **real** panel against a fake document and fire
  **real** pointer events:
  - hovering a +2 STR ring writes `70` with class `bw-vnum bw-up` and a sibling
    reading `(+2)` also `bw-up`; health reads `195 bw-up` behind a `194 / `
    prefix; DEX stays `50 bw-vnum`; the carry limit under the pack reads
    `180 bw-up`.
  - `pointerleave` puts back `68` and `bw-vnum` with an empty delta, and health
    back to `194`.
  - hovering a greatsword with a kite on writes parry `0%` with `bw-down` and
    `(-18%)`, and it comes back to `18%` on leave.
  - the tooltip carries `bw-tip-main` and `bw-tip-cmp`; the card is headed
    Equipped, names "Kite Shield", and says "in your off hand". An empty slot
    says "nothing worn there".
  - double clicking the ring leaves STR at `70` with class `bw-vnum` and no
    delta, puts the ring on `ring1`, and says "you put on ring".
  - clicking the shield on the doll takes it off, drops parry to `0%`, and says
    "you take off kite shield".
  - a real `drop` event from pack slot 2 onto the main hand equips and says so;
    a real `drop` from the main hand onto pack slot 5 unequips and says so.
  - a warhammer at 20 STR warns **on the card** before the click and refuses
    with the same sentence after it, and stays in the pack.
  - B lights the pack, it is still lit after `tick(1.0)` and dark after
    `tick(2.0)`; C leaves it unlit.
  - two `tick(0.3)` calls under a live hover leave the green 70 standing.
- **win_bag**: 73 checks. The four real `dblclick` cases are unchanged and now
  run through `buildBag`, which is the path the game runs. New: the panel has
  no `build`; hovering tells the listener which item and index and asks for the
  card for that same item; an empty slot hovers `null` and asks for no card;
  equipping fires `onChange` once and releases the hover first; a pack to pack
  drop moves the sword and says "longsword goes into slot 7 of the pack" though
  `inventory.move` said nothing; a drop onto the slot it came from says
  nothing; the carry limit is its own element reading `160` with `10.5 of `
  before it and ` stones` after.
- **windows**: 130 checks. Five tabs, `character,skills,abilities,crafting,map`,
  and no Inventory tab. `bag` and `inventory` both resolve to `character`;
  `open('bag')` lands on Character and counts as open under either name;
  `close('bag')` shuts it; C opens with no focus, B opens the same page with
  `focus: 'bag'`, the older `inventory` name with `focus: 'inventory'`; C then
  B closes the codex. With no character page registered the pack opens as
  itself. In the DOM section the strip holds **three** tabs for four registered
  panels, the Character tab's cap reads "Character, key C or B", `bodyOf('bag')`
  is the Character page, `open('bag')` turns back to Character **without
  building a fourth page**, and `refresh('bag')` rebuilds the same one.

## What is NOT verified

- **Nothing here has been looked at.** Every claim about the three column
  layout, the widened frame, the second tooltip card sitting beside the first,
  the green and the red, and the pack's soft highlight is a claim about CSS
  that has been parsed by nobody. There is no browser in this pass. Fable's
  screenshots are the first real test.
- **The column arithmetic is arithmetic, not a screenshot.** 280 + 424 + 400
  plus 32 px of gaps is 1136 inside a 1260 px body, and `repeat(auto-fill,
  52px)` at 7 px gaps in a 372 px content box gives six columns. None of it has
  been laid out by a layout engine.
- **The drag was exercised through `drop` events, not through a real drag.**
  `dragstart` sets a payload on a `DataTransfer` this test supplies by hand.
  The browser's own drag image, the `dragover` highlight and the `effectAllowed`
  negotiation have run zero times.
- **The paper doll still has not rendered a pixel**, which is U1's note and is
  unchanged. What did change here: `main.js` line 857 runs
  `ctx.paperdoll.update(dt)` every frame, and the page used to run it again in
  its own `tick`, which turned the figure at twice the speed it was written
  for. The page now winds the clock only on a doll it built itself.

## Two things found and NOT fixed, because they are not my files

1. **`actor.js`'s `recompute` never adds an armour tier's innate `resist`
   block.** `items.js` gives Platemail `{ physical: 3, fire: 2 }` per piece and
   `inventory.js`'s `resistsOfCharacter` sums it, but `recompute` sums
   resistances from **affixes only**. The fight reads `actor.resists`, so those
   innate resists currently do nothing in combat, and the sheet shows them only
   when there is no live actor. The preview reads the actor, which is the
   fight's truth, so a plate chest with no resist affix previews no resist
   change. That is honest and it is also wrong, and the fix belongs in
   `actor.js`. It is recorded in `compare.js`'s header so the next reader does
   not think it is an oversight here.
2. **The HUD portrait freezes when the Character page is closed.**
   `main.js` hands `ctx.paperdoll.canvas` to `hud.setPortrait`, and nothing but
   `win_character` ever calls `paperdoll.setVisible`. Closing the page turns
   the doll off and `paperdoll.update` returns false, so the portrait stops.
   Leaving it on would stall the GPU with a `readRenderTargetPixels` every
   sixty seven milliseconds forever. Whoever owns the portrait should decide;
   the page kept U1's behaviour rather than guessing.
