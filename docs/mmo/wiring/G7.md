## 1. `takesRarity(baseOrItem)`, which U1 and U2 asked for

```js
import { takesRarity, RARITY_KINDS, NO_RARITY_KINDS } from '../mmo/items.js';

takesRarity('longsword')                     // true
takesRarity(item)                            // reads an item record too
takesRarity('carrot')                        // false
takesRarity('moonsword')                     // false: not a base at all
```

It is declared near the top of `items.js`, above `STACKS`, so importing it costs
nothing and nothing has to be loaded in a particular order.

True for the six equipment kinds: `weapon`, `shield`, `armour`, `jewellery`,
`offhand`, `instrument`. False for `material`, `food`, `meal`, `potion`, `tool`,
`ammunition`.

Measured, over every base in the game rather than a sample:

```
every kind in the game is on one side of the rarity line or the other
  armour, food, instrument, jewellery, material, meal, offhand, shield, tool, weapon
80 bases take rarity and every one of them is gear
86 bases do not, and not one of them is gear
```

`auditItems` throws if a base ever has a `kind` that is in neither list, so a
seventh kind added tomorrow has to say which side it is on.

### What follows from it

- `makeItem({ base: 'carrot', rarity: 'legendary', affixes: [...] })` returns a
  common, identified carrot with no affixes. It coerces rather than throwing on
  purpose: `rollDrop` picks a rarity before it knows which base it drew, an old
  save can hold a green apple, and the dev bench lets you type anything. All
  three should end at one carrot, not at an exception.
- `rollAffixes` returns `[]`, `withAffixes` returns **the same object**, and
  `identify` returns **the same object**. Not a copy: a stack of carrots is not
  quietly replaced by one carrying an empty array.
- `rollDrop` and `bossRoll` never write a rarity above common onto one, and a
  boss's `floor: 'epic'` does not lift a haunch of venison.
- `bagColour` ignores them, so a sack of nothing but meat is not lit as if it
  held a white item. A purple in with the venison still reads purple.
- `describe` says `food`, not `Common food`.

## 2. Rarity IS the chance of an effect

That was already true for gear and is now proved out loud. A longsword, 1000
seeds per tier, printed by `affixes.test.mjs`:

```
common 0 (want 0), uncommon 1 (want 1), rare 2 (want 2),
epic 3 (want 3), mythic 4 (want 4), legendary 6 (want 6)
```

Legendary is five affixes plus one named power. Common rolls none at every one
of the thousand seeds; every tier above it rolls at least one at every seed.

## 4. Meat is never "meat"

Sixteen monsters carry the word `meat` in `lootTable`. They all used to join to
the one `food` base, so a giant rat, a bear and a harpy left the same grey
stack. `itemBaseFor` now takes the monster:

```js
itemBaseFor(word, tier = 1, monster = null)
```

`MEAT_OF` is the row, per monster id, and wins over everything. `MEAT_BY_KIND`
is the fallback on the `kind` field `monsters.js` already carries.

| monster | meat |
| --- | --- |
| deer | `venison` |
| rabbit, squirrel, gull, frog, crow | `game_meat` |
| fieldMouse, giantRat | `rat_meat` |
| caveBat, harpy | `game_meat` |
| crab | `crab_meat` |
| wolf, direWolf, werewolf | `wolf_meat` |
| boar | `boar_meat` |
| stonebackBear | `bear_meat` |

Fallback by kind: `critter`, `flying` and `beast` give `game_meat`, `vermin`
gives `rat_meat`, and **`undead`, `construct`, `elemental` and `humanoid` give
`null`**: a skeleton is bone, a golem is ore, and you do not butcher people.
None of those four carries `meat` today; the fallback is what happens the day
one does. Driven both ways in the test with three synthetic monsters: the word
resolves to nothing and simply falls out of their table, leaving the rest.

`itemBaseFor('meat', 1)` with no monster returns `null`. There is no item called
meat, so there is no honest answer to the word on its own.

`auditLootWords()` was rewritten to walk monster by monster (it used to walk the
set of distinct words, which cannot answer `meat` any more) and now also proves
every resolved meat is one of the seven `MEAT_BASES`. It reports
`{ words: 34, unjoined: 1, meats: 7 }`: all seven meats are reachable from a
real monster, so none is a base nothing can drop.

## 6. What other owners must change

### 6a. `win_bag.js` USABLE. This one matters most.

```js
// src/game/win_bag.js:27, as it stands
export const USABLE = ['potion', 'food', 'bandage', 'venison', 'game_meat'];
```

`'food'` is now a dead id, and **none of the seventeen foods, none of the six
meals and none of G6's twenty two forageables or twenty two products is in this
list**, so a double click on a carrot says "carrot is a material" and the pack
offers no Use. Every effect in section 3 exists and no player can reach it
through the bag. `USABLE` also decides the `consumables` filter row, so all of
it currently files under `materials` or `other`.

The list is the wrong shape. An item is usable when its base says what using it
does, and `items.js` is the only place that is written:

```js
// src/game/win_bag.js
import { baseFor } from '../mmo/items.js';

/** Usable when the base says what using it does. items.js `use` is the one field. */
export const usable = (item) => !!baseFor(item)?.use;
```

then `USABLE.includes(b.id)` becomes `usable(b)` at both call sites (`categoryOf`
line 47 and `actionFor` line 63). `bandage` has no `use` block and stays a
special case; keep it named, or give it one.

Owner: whoever holds `win_bag.js` (U1/U2 or W3). This is the difference between
food that works and food that looks broken.

### 6c. `win_crafting.js` should look at a base's material

`countMaterial` and `takeMaterial` gate on
`isRawMaterial = baseFor(it)?.kind === 'material'` and match on
`it.material === id || it.base === id`. Every meat carries `material: 'meat'`
**on its base**, which is how the six kitchen recipes that ask for `meat: 2`
could be paid in rat meat or venison. Two small changes make that real:

```js
export const isRawMaterial = (it) => {
  const k = baseFor(it)?.kind;
  return k === 'material' || k === 'food';        // raw meat IS a crafting material
};

// and in countMaterial / takeMaterial, also match the base's own material:
const mat = it.material ?? baseFor(it)?.material;
if (isRawMaterial(it) && (mat === id || it.base === id)) ...
```

Nothing regressed by leaving this alone: `venison` never matched `meat` before
either, so those six recipes have never been payable. This makes them payable.
`fish` already works, because the base id is the material id.
