# R1: the boot, in modules

`src/game/main.js` was 966 lines and knew every module in the game. It is now
about 100, and knows none of them. The game is a list of systems.

```
src/game/main.js            scene, save, the creation gate, the list, the loop
src/game/app/context.js     what every system may reach, and the frame record
src/game/app/system.js      the contract, the build order, the frame phases
src/game/app/systems/       one file per concern
  index.js                  the list, in frame order
  world.js player.js combat.js abilities.js inventory.js
  world_life.js ui.js dev.js input.js
```

Nothing about the game changed. This is a refactor: the same modules are
created in the same order, with the same arguments, and the frame does the same
work in the same order. The differences that are not zero are listed at the
bottom of this file, with why each one cannot be seen.

## The system contract

```js
system = {
  name: 'combat',
  deps: ['player'],              // names that must exist before create runs
  create(ctx) -> instance,       // registered on the context under `name`
  ready?(ctx),                   // once, after every system has been created
  hotkeys?(ctx, frame),          // keys that are not movement
  click?(ctx, ray, frame),       // return truthy to say "I handled it"
  move?(ctx, frame),             // whoever moves the eye this frame
  update?(ctx, frame),           // the world and the fight
  late?(ctx, frame),             // whatever reads what the fight decided
  render?(ctx, frame),           // the picture
  save?(ctx),                    // on the save tick and on the way out
  dispose?(),
}
frame = { dt, now, nowS, day, night, centre }
```

Most systems only want `update`. A system that wants none of the hooks is still
a system: `create` alone is a perfectly good one.

### Why six per frame hooks and not one

The frame has joints, and the old file had all of them. A single pass in list
order would put the player's pools before the fight that empties them, and the
picture before the things it draws.

| phase | what belongs in it |
| --- | --- |
| `hotkeys` | keys pressed this frame, before anything reads their effect |
| `click` | the click, first handler wins |
| `move` | the player walks, or the dev camera flies. Sets `frame.centre` |
| `update` | the world streams, monsters queue, the resolver settles, the bars react |
| `late` | pools, the death count, the target ring, the HUD: anything reading what the resolver wrote |
| `render` | sky, then the water that reflects it, then the frame |

`frame.centre` is written by the player system during `move` and read by
everything after it, so the world streams around where the eye is now rather
than where it was last frame.

### Two orders, and they are not the same order

`deps` decides what is **built** before what. The list decides what **runs**
before what. They were never the same: the window layer has to exist before the
ability bar can ask it whether a window is open, and the ability bar still runs
after the fight.

```
build order  world player combat inventory abilities ui emotes world_life events story sound net cellar_raid context_menu dev input
frame order  world player emotes combat abilities inventory world_life events story ui sound net cellar_raid context_menu dev input
```

Both are checked in `src/game/wiring.test.mjs`, by name.

### Wiring late

A system built early cannot hold a reference to one built late, so **the later
one holds the wire**:

- `combat.js` registers `combat.onDeath`, which calls `ctx.get('player').die()`.
- `abilities.js` registers `combat.onHit`, which bursts an effect.
- `dev.js` fills in `panelCtx.dev` and `panelCtx.debug` and applies the saved
  settings, because the settings window can turn fly mode on.

Anything that runs after the boot may simply call `ctx.get(name)` at the moment
it fires. The rule with teeth, and the test enforces it: **during `create`, a
system may only reach systems it declared in `deps`**, because the runner has
not built the others yet.

## How to add a system

1. Write `src/game/app/systems/<name>.js`:

```js
export const weather = {
  name: 'weather',
  deps: ['world'],                       // what must exist before this is built
  create(ctx) {
    const { sc, hud } = ctx;             // core services
    const runtime = ctx.get('world').runtime;
    const rain = createRain(sc, runtime);
    return {
      rain,
      bw: { rain },                      // what the console gets on window.__bw
    };
  },
  update(ctx, frame) { ctx.get('weather').rain.update(frame.dt, frame.now); },
};
```

2. Add it to `SYSTEMS` and `FRAME_ORDER` in `app/systems/index.js`, at the point
   in the frame where it should run.
3. That is all. `main.js` is not edited.

If it needs to be reached by name from elsewhere, it already can be:
`ctx.get('weather')`. If it wants a click, give it a `click(ctx, ray, frame)`
that returns truthy when it took one; it will be offered the click before every
system listed after it.

### The order of a click

The whole click lives in `input.js`, as one router, because its order is not the
system order and never was:

```
a held spell, a sack, a person, a station, a plant, a monster, a body, interact
```

A held spell is first because it is choosing who to hit, not starting a fight.
A new clickable thing that belongs at one of those points goes in that function;
a new clickable thing that belongs before all of them can be a system with its
own `click`, listed before `input`.

### The context

```js
ctx = {
  container, hudRoot, THREE,
  sc, state, hud, audio, floaters, input, camera,   // exist before a character does
  get character(),
  frame,                                            // the live record above
  aim(),                                            // the one raycaster, aimed now
  isNight(nowMs),
  register(name, system), get(name), has(name), names(),
  bw,                                               // the core half of window.__bw
}
```

`get(name)` throws with the list of what does exist rather than handing back
`undefined`; `has(name)` is the soft form. A name is registered once and never
again.

### `window.__bw`

Every key the single file exposed is still there, with the same meaning. Each
system declares its own share as `bw` on its instance, and `main.js` merges
them with `Object.defineProperties`, so the getters (`attacking`, `dying`,
`fps`, `codexTab`, `devBench`, `playerActor`, `character`, `now`) stay live.
`wiring.test.mjs` holds the list of all 53 keys and fails if one goes missing.

## What is not bit for bit the same, and why none of it can be seen

Measured, not asserted: these are the only orderings that moved.

1. **npcs, stations and forage now update after the fight rather than before
   it.** None of the three reads or writes anything the resolver touches. A
   plate moves one frame later relative to a swing that cannot see it.
2. **The loot bags age inside `combat.update` rather than after the ability
   bar.** `loot.update(dt)` only counts a bag's ninety seconds down.
3. **The target ring, the effects and the trade channel run before the HUD
   rather than after it.** All three write to things drawn later in the same
   frame, and the HUD reads none of them.
4. **The HUD, windows, paper doll and compass now run before the sky and the
   water.** They are DOM and canvas work; the sky is a shader. Neither reads
   the other.
5. **`tickPools` runs before `combat.update` rather than after it.** The flinch
   check stayed exactly where it was, immediately after `combat.update`, so the
   interval it compares over is unchanged. Regeneration between two frames is
   applied at a different point inside the same gap; a hit smaller than one
   frame of regeneration was invisible before this change and still is.
6. **The settler's kit is granted in `inventory.js` rather than in the player's
   block.** It runs in the same breath as `createInventory`, as it did, so the
   boot log reads in the same order.
7. **`effects` is created after the target ring rather than before it.** Both
   add transparent objects to the scene; three.js sorts transparent draws by
   depth, not by the order they were added.
8. **The opening line is toasted before the first frame is scheduled rather
   than after.** The saved settings, the dead at boot wake and the opening line
   still happen in that order, which is the order the single file had them in.
   `window.__bw` is still the last thing the boot does, which is what the
   watchdog in index.html waits for.

## Verified

- `npm test`: all suites green. `wiring.test.mjs` went from 115 checks to 160.
- `npx vite build`: clean, 123 modules.
- `wiring.test.mjs` drives the real runner with fake systems: build order,
  cycle detection, a missing dependency, the click stopping at the first
  handler, ready and save in list order, dispose in reverse, and the four ways
  a malformed system is refused.
- The real list is checked by name against the frame order, every dependency is
  resolved, the whole list is sorted, and no system reaches an unbuilt system
  while it is being built.
- The old file was read line by line against the new ones: every method call it
  made is still made, and the two that are made fewer times (`heightAt` and
  `camera.snap`) were repeated literals that are now one function each.

## Not verified

Nothing here was run in a browser. `main.js` and the nine systems need a
document, a renderer and a WebGL context; the checks on them are source checks
and say so in their names. That the game boots and plays the same is Fable's to
confirm.
