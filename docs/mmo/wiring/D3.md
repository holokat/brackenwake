# D3: caverns, the boxes in them, and the boss at the bottom

Wave B, the third of four. A second generator beside the room and corridor one,
a table that says which places use it, chests you have to get into, and the
sheet's own boss standing in the hall at the bottom.

| file | what it is |
| --- | --- |
| `src/mmo/dungeons.js` | new. The table: kind, levels, theme, arena, chests, caches, boss and tier for all 13 ways down, with `auditDungeons` both directions at import |
| `src/world/cavern_gen.js` | new, pure. `generateCavern(seed, site, level, spec)`: dungeon_gen's layout plus heights, bridges, gorges, water, boxes and an arena |
| `src/world/cavern_scene.js` | new. `createCavernScene(THREE, layout)`: floors at their heights, risers, walls, a roof that follows the ledges, pits, planked spans, pools, clickable boxes, nine themes, eight lights |

## 1. Wiring Fable has to do

Four files, none of them mine. Until they are in, a chest is something the
cursor finds and nothing opens.

### `src/game/state.js`, the character document

In `blankCharacter()`, beside `uniques`:

```js
    opened: [],           // chest keys already emptied, once each (D3)
```

In `hydrate()`, beside the `uniques` line:

```js
  // the boxes this character has already emptied (D3): a chest pays once ever,
  // so the list has to survive a reload or every level is a fresh payday
  if (Array.isArray(raw.opened)) doc.opened = raw.opened.filter((k) => typeof k === 'string');
```

Without it `chests.js` still keeps the list on `character.opened` in memory, so
the whole path runs and only the reload loses it. The save writes the whole
document (`JSON.stringify(doc)`), so the list is already WRITTEN to localStorage
today; it is `hydrate` that drops it on the way back in, which is the one line
above. `chests.js` calls `state.touch('opened')` when it writes, which `notify`
already accepts.

### `src/game/app/systems/world.js`, one sentence that is now untrue

`onDungeonState` says, of a dungeon with boxes in it:

```js
          : (st.chests ? ` ${st.chests} chests down here, and no way into them yet.` : '');
```

There is a way into them now. It should read:

```js
          : (st.chests ? ` ${st.chests} boxes down here, and a pick opens the locked ones.` : '');
```

A cave takes the `st.kind === 'cave'` branch and only counts its ore, so a
cavern built for a cave says nothing about its boxes. That is worth a word too,
and it is that file's line to write.

### `src/game/interact.js`, the cursor

One import, one branch in `decide`, one case in `act`, one line in `hoverText`,
and one word in `enter`.

```js
import { CHEST_REACH } from './chests.js';   // the reach only; the runtime is built in world_life.js
```

`decide`, after the `pick.kind === 'site'` branch:

```js
  if (pick.kind === 'chest') {
    const c = pick.chest;
    if (!c) return { action: 'none', reason: 'nothing' };
    const d = horiz(playerPos, c);
    if (d > CHEST_REACH) return { action: 'blocked', reason: 'too_far', chest: c, dist: d };
    return { action: 'open', reason: c.kind, chest: c };

```

`createInteract`'s signature gains `chests`, and `act` gains a case:

```js
      case 'open': {
        chests?.open?.(d.chest, { at: player?.pos });
        return d;
      }
```

`hoverText`, beside the site branch:

```js
    if (pick.kind === 'chest') {
      const c = pick.chest;
      if (!c) return '';
      const noun = c.kind === 'cache' ? 'a cache' : c.locked ? 'a locked chest' : 'a chest';
      const d = horiz(player?.pos, c);
      return d > CHEST_REACH ? `${noun}, too far` : `${noun}, E to open`;

```

`enter()`, so E reaches a box the way it reaches a mouth:

```js
      if (d.action === 'enter' || d.action === 'exit' || d.action === 'open'
        || (d.action === 'blocked' && (d.site || d.chest))) return act(d);
```

The `blocked` / `too_far` line in `act` already says "too far, get closer" for
anything with no site on it, so a box out of reach speaks without further work.

## 2. What was built, and the decisions inside it

### The table, `src/mmo/dungeons.js`

Thirteen rows: the sheet's eleven dungeons and two caves. `levels`, `boss` and
`tier` are read out of `realms.js` and `BOSS_BY_LAIR` rather than typed again;
`kind`, `theme`, `chests` and `caches` are this file's own.

Which places are caverns is decided by the sheet's own `geography`, sentence by
sentence. Built things stay on the old generator: brick cellars under a mill,
galleries cut behind a cliff, a foundry with walkways over furnaces, a buried
tower, a marble palace, a fortress in a crater wall. Hollow things become
caverns: a sea cave, a crater's throat, a shaft cut down through a peak, a
dragon's neck bones, a cutting through a glacier, a sinkhole maze, a cave behind
a waterfall. Seven caverns, six rooms.

**The ninth theme.** WAVE-B names eight stones for nine realms. The Eyrie's
Roost is cut into a mountain and is none of them, so granite is the ninth and
the audit counts nine.

**The Brass Works.** The sheet gives `brasscity_works` the boss line "The Brass
Heart", and the roster lairs the Brass Heart at `firstfire`. They are the same
fight met two ways, so the Works carries `boss: null`, keeps its arena, and the
arena falls back to the habitat's own boss roll. `auditDungeons` allows exactly
that one case, by name, and fails for any other arena with no boss.

**The wandering two.** `noon` lairs at a road and `rimemouth` at a wood, and both
carry the `wanders` tag. The audit requires that neither has a dungeon, so E2
owns them and D3 cannot quietly stand a second copy underground.

### The heights, and why a step is never a cliff

The rule is not checked after the fact, it is impossible to break. Chamber
heights are a random walk of two to six metres, put through a min-plus closure
against the real grid distance between the chambers, so a pair joined by a short
passage has its difference cut to what that passage can ramp. Every cell's
height is then the average of two envelopes computed by multi-source Dijkstra
over the walk grid: `min(T + distance)` and `max(T - distance)`. Both are
1-Lipschitz, so their average is, so two neighbouring walkable cells differ by
at most one step of 1.0 m, under the 1.2 m a player may climb.

The average matters. The upper envelope alone puts a hill in the middle of every
long passage and the lower one digs a trench there. Averaged, a passage reads as
flat ground, a ramp, and flat ground again, and a dead end stays level.

A drop that is a real drop is a GORGE, and a gorge cell is not walkable at all.
Only rock ever becomes gorge, never floor, so a bridge can never sever a level.

### The player, the camera and the monsters on a ledge

`runtime.heightAt` underground now answers `floorAt` for the cell under the
point, and `DUNGEON_FLOOR_Y` on a level with no heights, which is every level the
old generator builds. That one function is the whole path:
`app/systems/player.js` walks the rig with it, `keepInside` re-reads it after a
clamp, and `monsters.js` takes every body's y from it, so a wolf on a ledge
stands on the ledge without another line being written.

`cameraClamp` reads the floor under the camera as well as the roof over it. On a
chamber twelve metres down the old clamp held the camera at 0.9 m, which is
eleven metres over the player's head and out through the roof.

### The boss

`BOSS_BY_LAIR[site.sub]` decides, through the layout: `world_runtime.dungeonLayout()`
adds `arena` and `bossLair`, `normalizeDungeonLayout` carries both, and
`bossRowsFor(habitat, lair)` returns that lair's boss and no other. This works
for BOTH generators, so Malachar stands in the Throne of Ash's deep room as well,
which he did not before: the habitat used to roll one of four.

The boss's minions are its own `summons` row, called in the fight by the phase
plan in `monster_ai.BOSS_PLANS` and `monsters.js summonFor`. Nothing is
pre-placed, because pre-placing would double what the row already delivers and
would break the standing rule that the boss's hall holds the boss and nothing
else.

**The banner uses `onZone`.** It is the only words path that reaches
`hud.zone(name, sub)`; `onDungeonState` only toasts. `world_runtime.checkArena`
fires it the first time the player's cell is inside the arena room, once per
level built, with `{ id, name: the boss's name, danger: [tier, tier], line }`.
`zoneSub` reads `danger[1]`, so the subtitle is the realm's own danger word, and
`app/systems/world.js` records the id on `character.zones` exactly as it records
a region.

### The boxes, in both kinds of level

One case is never the case. The six places that keep the old generator had boxes
already, drawn as merged meshes with nothing on them, which is why
`app/systems/world.js` said "no way into them yet" every time you went down. So
`dungeon_gen.js` now dresses its tagged cells into the SAME record `cavern_gen`
writes (`kind`, `locked`, `trapped`, `tier`, `key`, world x and z), and
`dungeon.js` builds each as its own group with `userData.chest`, a hinged lid and
an invisible target, with the same `openChest` the cavern scene has. One file
opens a box and it does not matter which generator built the level around it.

A rolled shaft in the hills, which has no row in the table, keeps the count it
always had and every box on it is a locked chest, exactly as before.

A chest is locked and rather more than half the time trapped; a cache is
neither and holds one thing. Both are placed out of the entry room, off water,
off the entrance and the stair, off a gorge, and never within three cells of
each other.

Opening one is three gates in order: reach at 3 m, then the trap, then the lock.
The trap is a Remove Trap roll and is spent either way, so a box is never a wall.
Damage is tier x 8 through `combat.hurt`, the same call a fall comes through.
The lock is a Lockpicking roll and wants a lockpick in the pack; one failure in
four snaps it, and the words say how many are left. Both rolls teach through
`progression.lesson`, which is `rollGain` in `skills.js` and therefore the bands,
the 100 cap, the 700 cap and the half chance on a failure.

**`successChance` is invented and says so.** 01-STATS-SKILLS gives a gain curve
and no success curve. This is a straight line through the difficulty: even money
at the difficulty itself, 0.95 at 25 points over it, 0.05 at 25 under, clamped so
no box is impossible and none is free. Difficulty is 20 a tier.

The payout is `rollDrop` at the realm's danger tier, which is the same roll and
the same class bias a kill goes through, two to four items from a chest and one
from a cache, plus the tier's gold band times three. What the pack refuses goes
on the floor as a sack through `loot.drop`, and the line says so.

## 3. What was measured

Every number below is printed by a committed suite. `npx vite build` is clean.

**`src/world/cavern_gen.test.mjs`, 50 checks.** All 7 sheet caverns at all 14 of
their levels:

- every floor cell of every level is connected to the mouth: 14/14 levels
- walking it needs no step over 1.2 m: 0 levels with anything stranded, and the
  worst step anywhere on any level is **1.00 m**
- the same gate driven false: a 3 m step planted between two cells is refused by
  `stepOk` and really does cut 1 cell off the reachable set, and putting it back
  makes the level whole again
- the arena is on the last level of all 5 caverns that have a boss and on none of
  the other 9 levels; it is 448 to 780 m2, at least half again the middling room,
  and always the room furthest from the mouth
- 98 boxes: 0 in the entry room, 0 in water, 0 over a gorge, 0 off the floor,
  0 pairs stacked, 0 levels outside their spec's count, 43 locked and 20 of those
  trapped
- chambers: 84 of 99 neighbouring pairs stand 2 m or more apart, and a level
  rises and falls 8 to 16 m across
- 14 of 14 levels have a span, and all 707 gorge cells are rock rather than floor
  taken away
- determinism: the same site, depth and seed build the same cells, heights,
  boxes and arena; a different depth, place or world seed do not
- one level takes **2.3 ms** to generate

**`src/game/chests.test.mjs`, 75 checks**, driven through the real

- a trap drawn takes 0 health; a trap sprung takes exactly 32 at tier 4 through

- 120 tier 1 boxes take Lockpicking from 0 to **34** and Remove Trap to **34**
- and the join to the generator: a real chest off level 1 of the Trophy Throat
  opens, at tier 4, remembered by the key the layout wrote, refusing the second

## 4. What is NOT verified

- **Nothing has been seen in a browser.** Every measurement above is node. The
  colours of the nine themes, the look of a pit under a bridge, and whether a
  riser between two ledges reads as a step rather than a seam are unverified.
- **`chests.js` is not in the bundle yet**, because nothing imports it until the
  wiring in section 1 is in. Its own suite drives the real pack, the real
  progression and the real loot roll, so the module is proved; the click that
  reaches it is not.
- **`character.opened` does not survive a reload** until the state.js line is in.
  The list is written and read on the character either way, so the once-ever rule
  holds inside a session and only across one is missing.
- **The trap has no sound of its own.** It plays `denied`, which is the refusal
  cue. A needle going into a hand deserves better and there is no cue for it.
- **No cavern has been walked.** The reachability proof is a flood fill over the
  same step rule the player obeys, which is the strongest statement short of
  driving the rig, but the rig has not been driven through a cavern.
- **The two caves keep their ore** and it is placed by the same rule the old
  generator used, but no pickaxe has been swung at a cavern seam in a browser.
