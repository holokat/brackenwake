# Z2: the world table is Brackenwake

Design note: `docs/mmo/09-WORLD-ZONES.md`. Read that first; this file is the
list of things other people's files now have to do, and the list of lines in
other people's tests that have to change.

**Owned and changed:** `src/world/zones.js` (rewritten), `src/world/field.js`,
`src/world/sites.js`, `src/world/zones.test.mjs`, `src/world/field.test.mjs`,
`src/mmo/realms.js` (the nine `x`, `z`, `r` values and nothing else),
`docs/mmo/09-WORLD-ZONES.md`, this file.

**Not touched:** `monsters.js`, `win_map.js`, `compass.js`, `world_runtime.js`,
`dungeon_gen.js`, `sitegrid.js`, `roads.js`, and every test file not listed
above. Section 5 is the list of lines in those tests that now say something
untrue, with the replacement measured rather than guessed.

---

## 1. What the table is now

```
104 zones = 9 realms (parent: null) + 95 subzones (parent: <realm id>)
46 authored sites, of which 9 are mines, carrying 27 cuts and 47 seams
```

Every one of them is generated from `src/mmo/realms.js` at import. `zones.js`
invents no place: it holds the engine's half of each row (how soft the edge is,
which of the eight biomes a realm's own biome word means, the climate nudge, the
ore band, the three word banner name) and one `LAYOUT` line per place saying
where it stands.

New exports on `zones.js`, all of them additions:

```js
REALM_ZONES        the nine, in the sheet's order
SUB_ZONES          the ninety five
subZonesOf(id)     one realm's places
realmAt(x, z)      the realm a point is in, whatever place is over it
weightOf(zn, x, z) how much of a zone a point is inside, 0 to 1
ORE_LADDER         the ten ores, poorest first
SEA, seaWithin, REEFS, reefWithin, reefTopAt, reefAt
ARCHIPELAGO, archipelagoWithin
discOverlap(a, b), SIBLING_OVERLAP
TOWN_PRECINCT_R, MAX_FLAT_R, CELL_PAD_MAX, SUB_COAST_KEEP, SUB_EDGE
```

`zoneAt` and `zoneBias` keep their signatures. `zoneAt` now scans two deep (the
nine realms, then only the children of a realm the point is already inside) and
came out **faster**, not slower: 0.083 us over 200000 lookups of 104 zones,
against 0.098 us over 21. `sampleAt` is 1.5 us, against 1.59 before.

## 2. What a caller has to change

### 2.1 `zoneBias` has a new field, and the old one now means something narrower

```js
const b = zoneBias(x, z);
b.id          // the DEEPEST zone: 'saltpans'
b.parent      // the realm record, or null when the deepest zone IS the realm
b.weight      // how far inside the DEEPEST zone   -> discovery, the banner
b.biasWeight  // how far inside the REALM          -> the climate, the override
```

If you were scaling anything by `zoneBias(...).weight` because you wanted "how
much of this country is this", you want `biasWeight` now. `field.sampleAt` was
the only caller and it has been changed. Nothing else read it.

### 2.2 `sampleAt` carries `realm` beside `zone`

```js
const s = field.sampleAt(x, z);
s.zone    // 'saltpans', the deepest zone, or null in unclaimed country
s.realm   // 'emberwastes', or null
s.danger  // [lo, hi], unchanged
```

`realm` is for M2: the roster's habitat column names realms, and a spawn table
that wants "what lives here" should key on `s.realm` and roll against
`s.danger`. Neither is read yet.

### 2.3 Discovery announces a realm and then a place

`discovery.checkZone(x, z, now)` still returns one zone or null and still fires
once per zone, ever. What changed is that it now walks the chain: standing in
Coldseat with nothing found, the first call returns **Frostreach** and the
second returns **Coldseat**. `main.js`'s `runtime.onZone` handler needs no
change at all; it will simply fire twice, which is what should happen.

`hud.zone(zone.name, zoneSub(zone))` also needs no change, but read what it now
says:

```js
zoneSub(ZONE.greenwold)   // 'quiet country'   a realm says its danger
zoneSub(ZONE.hearthhome)  // 'the Greenwold'   a place says its realm
```

New export from `sites.js` if you want the pair yourself:

```js
import { zoneChain } from '../world/sites.js';
zoneChain(x, z);   // [{ zone: realm, weight }, { zone: place, weight }]
```

### 2.4 An authored site's id changed shape, and so did the saved list

The old id was `z:<zone id>:<index>`, which renamed itself whenever a row moved
in the table. It is now `z:<place id>` out of realms.js, which is stable
forever. **Every discovered-site id in every save that referred to an authored
site is now stale**, and there are 46 of them against the old 30. A character's
`discovered` list holds strings and unknown strings are ignored, so nothing
breaks; a player who had found the Millrun Adit will simply find The Chalk Pits
again. There is no migration and none is worth writing: the zones those ids
belonged to no longer exist.

The same is true of `character.zones`: the 21 old zone ids are gone. A save
keeps them harmlessly (`zonesList()` filters unknown ids out) and will discover
all 104 new ones as it walks.

### 2.5 A site may now lay a pad wider than its own cell

Seven towns carry `flatR: 120` (`TOWN_PRECINCT_R`), which is wider than the
96 m margin sitegrid keeps round a site inside its 480 m cell. `field.sampleAt`
handles it: it keeps the short list of authored sites whose pads reach out of
their own cell and checks it by distance on every sample, so a precinct is level
right across a cell border instead of being cut off square on three sides.
Measured at Hearthhome: 32 points at 60 m out, the worst 0.000 m off the pad.

Anything else that reasons about "a site's footprint is inside its own cell"
needs to know that this is now true of rolled sites and of authored sites under
`CELL_PAD_MAX` (96), and not of the seven precincts. `flora.js` and `fauna.js`
read `flatR` and clear that radius, which is right and wanted.

### 2.6 A dungeon site carries `levels`, and nothing reads it

`authoredSites()` puts realms.js's own `levels` on each of the 11 dungeon sites
(1 for the Old Cellars, 2 for the Deep of Faces, 3 for the Throne of Ash).
`dungeon_gen.maxLevel(kind)` still returns a flat 3 for every dungeon in the
world. **The field exists and is decoration until `dungeon_gen.js` reads it**;
it is written here rather than left out so that the number lives in one file
when somebody wires it.

## 3. The Caldera Sea, for anyone drawing or swimming in it

```js
import { SEA, seaWithin, REEFS, reefAt, ARCHIPELAGO, archipelagoWithin } from './zones.js';
seaWithin(x, z)         // 1 in the deep, 0 outside SEA.edge, smooth between
reefAt(x, z)            // the reef you are standing on, or null
```

The sea is `field.raw`'s doing, so `heightAt`, `sampleAt`, the mesher, the water
plane, the map and the flood fill all already agree about it. It is water
(measured 1656 of 1656 samples), it is 18 m deep, it has a beach on its landward
side, and it is 2519 m from the origin at its nearest.

What is NOT built: **there is no boat**. Every one of the Sunken Kingdom's
places is reached by swimming, and `world_runtime` has no notion of a vessel.
Three of its buildings stand on named reefs so that a swimmer has somewhere to
stand up.

## 4. The heart is untouched, and here is the proof

`field.test.mjs` digests a 2 km square about the origin, 101 by 101 samples at
20 m, every field of every sample. The constant was taken from the commit before
`zones.js` existed.

```
ok  the 2 km square around the origin is bit for bit what it was before zones existed
    10201 samples, 6408cb4e64daf869...
```

It holds. Three separate rules keep it holding, and `auditZones()` measures all
three at import rather than inferring them from radii:

1. no biased zone wins anywhere inside `HEART_SAFE` (a 50 m grid over the whole
   1500 m disc). The first biased ground in the world is 1900 m out.
2. no authored site stands inside `HEART_SAFE`, and none owns one of the 36
   site cells the digest samples. The nearest site is 1644 m out.
3. the Caldera Sea's outermost reach stays outside `HEART_SAFE`. It is 2519 m.

Line 21 asserts that no site's pad is wider than its cell's margin:

```js

```

That is still true of every ROLLED site and is now false of the seven town
precincts, which `field.sampleAt` handles by looking at the neighbouring cells

### `src/world/flora.test.mjs` (1 failure)

Line 175 wants boreal to be thick:

```js
(perBiome.boreal.fir || 0) > 100 && (perBiome.boreal.spruce || 0) > 100 && (perBiome.boreal.pine || 0) > 50
```

Brackenwake has no conifer realm. Boreal fell from 9.0% of the world to 3.3%,
because the old table had five cold climate nudges spread across it and the new
one has two, both of them under a hard override. Measured over the same 40
boreal chunks the test finds: **fir 66, spruce 77, pine 66, birch 47**. The
shape of the claim is still right (two conifers and a birch through them); the
numbers want to be `> 50`, `> 50` and `> 30`. Measured with that change: **117
passed, 0 failed**.

This is a real change to the world and not a rounding: if less conifer forest is
the wrong answer for Brackenwake, the fix is a realm that is a conifer realm, not a
threshold.
