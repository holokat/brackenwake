# U4 wiring: the book of abilities, a second bar for what you carry, a ticker for what you learn, and one button that tidies the pack

Files owned and touched: `src/game/win_abilities.js`, `src/game/hud.js`,
`src/game/item_bar.js` (new), `src/game/inventory.js` (`sortRank`, `sortName`,
`sortOrder`, `sort`, and nothing else), their four `*.test.mjs`, and this note.
`windows.js`, `ui_theme.js`, `win_character.js`, `win_bag.js`,
`abilities_runtime.js` and `main.js` were read and not edited.

---

## 1. What changed, in a paragraph each

**The Abilities page is a book now.** It used to list what you had already
bought, in two flat columns of thirteen point text, which meant a player could
not know the game HAS a Fireball until the day Magery reached 25. A ladder you
cannot see is not a ladder. All seventy eight rows are drawn, grouped by
archetype, as cards in a grid that is two columns wide and falls to one when
the codex is narrow. A card is a 64 px art tile, the name in Cinzel at 18 px,
the cost and cooldown and cast time and range as small caps chips, the
description in Cormorant at 15.5 px, and a requirement line. What you have is
bright and draggable. What you have not is dimmed, wears a drawn padlock, and
says the sentence that would change that with your own number in it, live:
`unlocks at Swordsmanship 50, you are at 33.4`. A filter row runs All,
Unlocked, and then one chip per archetype. The twelve slot bar preview stays at
the top with its keys, and it is still a drop target.

**The art is drawn in code**, the way `ui_theme.js` draws the item glyphs.
Twenty five marks, one per effect kind: a blade for a `damageMult`, a bolt for
a `spellDamage`, a burst for an `aoe`, a heart for a `heal`, a shield for an
`absorb`, chains for a `control`, a skull for a `summon`, and so on. The mark
takes the archetype's colour and the tile behind it takes a wash of the damage
type when the row names one. `auditArt()` runs at import and throws if the
twenty seventh effect kind ever appears without a mark, or if any of the
seventy eight rows falls through to nothing.

**There is a second bar.** Eight slots, to the right of the twelve, on the same
centred rail with a gold rule between them. It takes the pack's own drag
payload. A slot remembers the item's **base**, never the pack index, so a stack
that moves when you loot something still fires. A consumable goes through
`ctx.useItem`, a weapon or a shield or a piece of armour goes through
`inventory.equip` and the slot then shows it worn and says which slot it went
to, a stack that has run out leaves a dimmed ghost of what was there rather
than an empty square, and every press says something.

**Gains moved to the bottom right.** `hud.gain(text, kind)` stacks lines that
slide in from the right over 0.25 s, hold 2.15 s and fade over 0.6 s, three
seconds in all. They used to be world floaters spawned at the player's own
feet, which is exactly where the label of the thing you just picked up is
drawn, so every lesson learned while looting sat on top of the loot.

**The pack sorts itself.** `inventory.sort()` folds stacks of the same base AND
the same material together, orders what is left by kind, then by name, then by
the bigger pile, compacts it to the front, and says the numbers in one line.

## 2. The create calls

### The item bar

After `inventory`, `input`, `hud` and `foraging` exist, and after `ctx.useItem`
is set (`main.js` line 358 today):

```js
import { createItemBar } from './item_bar.js';

const itemBar = createItemBar({
  character, inventory, input, hud,
  useItem: (item, where) => ctx.useItem(item, where),

  // optional, each degrades to a spoken "which code is missing" rather than silence
  setTool: (id) => pickTool(id),                    // see section 7
  enabled: () => !windows.anyOpen,                  // the same gate abilities_runtime takes
});
```

Then two lines that join it to the HUD:

```js
hud.onItem((slot, how) => (how === 'clear' ? itemBar.clear(slot) : itemBar.use(slot)));
hud.onItemDrop((slot, payload) => itemBar.assign(slot, payload));
```

and one in the frame, beside `abilities.update`:

```js
itemBar.update(dt);            // reads input.pressed for its eight keys
```

`itemBar.update` calls `input.swallow(key)` on the press it acts on, so nothing
later in the frame acts on the same key.

Nothing else is needed. In particular the bar needs no boot data: it repairs
`character.itemBar` itself, and a save written before this bar existed comes
back with eight empty slots.

### `window.__bw`

```js
window.__bw = { ...existing, itemBar };
// useful: __bw.itemBar.view(), __bw.itemBar.assign(0, { pack: 3 }), __bw.itemBar.keys()
```

## 3. `hud.update`'s view

One new field. Everything already there is unchanged.

```js
hud.update(dt, {
  actor,
  target: targeting.frame(character),
  bar: abilities.barView(nowS),
  buffs: abilities.buffsView(nowS),
  items: itemBar.view(),          // NEW. Eight entries, always.
});
```

`itemBar.view()` gives, per slot:

| field | what the HUD does with it |
| --- | --- |
| `slot`, `key`, `cap` | the key cap, top left. `cap` follows a rebind |
| `base`, `name` | the art, drawn through `ui_theme.itemGlyph`, and the title |
| `count` | the badge, bottom right, shown only above 1 |
| `have` | there is one in the pack right now |
| `worn`, `wornAt` | a gold ring on the cell and "on mainHand" across the foot |
| `ghost` | dimmed and greyscale: you had one, you have none |
| `empty` | nothing was ever put on this key |
| `kind` | `use`, `equip` or `tool`; there for a tooltip that wants it |

A missing `items` empties the row rather than freezing it, the same way a
missing `bar` empties the twelve.

**Also new on the ability bar, and it is G2's, not mine.** `drawBar` now reads
`e.unusable` and `e.unusableReason` off `barView`, greys the cell and puts the
reason in its title. G2.md asked hud.js for this in section 3 and hud.js
belonged to nobody in that wave. It is one word in the class name and one CSS
rule, both measured in `hud.test.mjs`, and it needs nothing from main.js:
`barView` already carries the two fields.

## 4. The progression routing line

**Already wired.** `main.js` lines 211 to 218 read:

```js
const gainFloaters = {
  spawn: (pos, text, kind, extra) => (kind === 'gain' || kind === 'stat') && typeof hud.gain === 'function'
    ? hud.gain(text, kind) : floaters.spawn(pos, text, kind, extra),
  get count() { return floaters.count; },
};
const progression = createProgression({ character, actor, floaters: gainFloaters, hud, audio, state });
```

`hud.gain` did not exist when that was written, so the `typeof` check has been
falling through to `floaters.spawn` every time. It exists now, so the branch
turns on with no edit at all. **Nothing to do.** A skill gain and a stat gain
go to the ticker; damage, misses, loot and falls still float in the world.

`hud.gain(text, kind)` takes `'gain'` (green) or `'stat'` (gold). An empty
string is refused rather than drawn blank. Six lines at once; the oldest is
dropped.

## 5. The Sort button

`inventory.sort()` exists and is measured. The button is one line in the
inventory grid's filter row, which is **U3's file** (`win_bag.js`):

```js
// beside the CATEGORIES chips in win_bag.js's filter row
const sortBtn = h('div', 'bw-cat', 'sort');
sortBtn.addEventListener('click', () => { inv()?.sort(); draw(); });
row.appendChild(sortBtn);
```

`sort()` speaks for itself through the same `say` every other pack operation
uses, so nothing else has to report it. The `draw()` is needed because the grid
does not redraw on `onChange` by itself.

`sortOrder(items)` is exported and pure, for anything that wants the ordering
without the side effects: `{ items, merged, moved }`, a dense array with no
holes, and it does not mutate a single record handed to it.

## 6. The keys

| key | what it does |
| --- | --- |
| 1 to 0, minus, equals | the ability bar, unchanged |
| **F5 to F12** | the eight item slots |
| F1 | fly mode, unchanged |
| F2 | the dev bench, unchanged |

**Why F5 and not F3.** F1 and F2 are taken, and the twelve number keys belong
to the ability bar. Starting at F5 leaves F3 and F4 free next to the two the
game already owns, which is a gap on purpose.

**What the browser does with them, measured against Chrome's behaviour rather
than assumed:**

- **F5 reloads the page.** `input.js` never calls `preventDefault` on a key, so
  left alone, pressing the first item slot would take the whole world with it.
  `item_bar.js` installs its own capture phase `keydown` listener on `window`
  and calls `preventDefault` on exactly the keys it is currently bound to,
  nothing else, and takes it back off in `dispose()`. A rebind takes effect on
  the guard at once. A press with ctrl, cmd or alt held is left to the browser,
  because those are its shortcuts and not ours.
- **F11 goes full screen.** Same guard, same fix.
- **F12 opens the developer tools, and a page cannot stop it.** This is a
  browser level binding above the page. Slot eight is therefore the one slot
  that does not work in Chrome with its default key, and the honest fix is to
  rebind it.

**Rebinding.** `character.settings.itemBar` is a plain array of eight key
names, exactly the shape `settings.bar` already has for the ability bar, and
`itemBar.rebind(slot, key)` writes it. It refuses `windows.RESERVED_KEYS` (read
from windows.js, not copied), the twelve ability bar keys, F1 and F2, and a key
another item slot already holds, and it names which in every case.

`win_settings.js` is not mine and was not edited. When somebody wants a row of
rebind buttons for these eight, `rebind` is the function and `SETTINGS` in
`win_settings.js` is where the row goes.

## 7. The tool slot, and what is not reconciled

A pickaxe is an item in the pack with `kind: 'tool'` and no slot. The HUD tool
row is a different system: `state.tools` is a set of ids you have BOUGHT, and
`main.js`'s `pickTool` refuses an id that is not in it. So a pickaxe you looted
and a pickaxe you own are two unrelated records, and neither this file nor
`hud.js` can join them.

Rather than guess, `item_bar.js` treats a tool as its own third answer:

- with no `setTool` hook, pressing a tool slot says *"Pickaxe is a tool, and
  nothing is wired to take one in hand from a slot yet; main.js passes setTool
  to createItemBar"*, which is W4 §8's pattern: name the missing code, do not
  eat the press.
- with `setTool: (id) => pickTool(id)`, the press goes through main.js's real
  `pickTool`, and if the id is not in `state.tools` main.js's own refusal is
  what the player hears.

**That refusal will read strangely** for a pickaxe you are holding: "you do not
own a pickaxe yet". The real fix is for `state.tools` and the pack to agree,
which is `state.js` and `main.js`, neither of them mine. Both branches are
measured in `item_bar.test.mjs`.

## 8. Invented here, and why

| thing | why | where |
| --- | --- | --- |
| **A locked card names ONE weapon skill, not "a weapon skill"** | Power Strike, Whirlwind and Leap Slam gate on `skillAny`. "unlocks at a weapon skill 50" is a shrug; "unlocks at Swordsmanship 50, you are at 33.4" is a sentence a player can act on. The skill named is the one of the four the character is best at, which is the number the gate actually reads | `win_abilities.js` `requirementParts` |
| **A two branch row reports the branch you are closest to finishing** | Snare and Resurrect are the only two with `anyOf`. Printing both branches is a paragraph; printing the nearer one is an instruction. It switches branch as the numbers move | same |
| **Nine archetype colours** | no document names one. Presentation values chosen to read on dark stone next to the gold; nothing else reads them | `win_abilities.js` `GROUP_COLOUR` |
| **Twenty five marks, keyed by effect kind and not by ability** | seventy eight hand drawn icons would rot the moment a row changed. One mark per effect kind means a new ability gets art for free, and `auditArt` fails loudly if a new KIND arrives without one | `win_abilities.js` `ART`, `ART_ORDER` |
| **Eight item slots** | no document names a number. Eight is what fits beside twelve on one rail at 1280 px, and it is `ITEM_KEYS.length`, never a number typed twice | `item_bar.js` |
| **A slot remembers the base, not the item** | the brief asked for the base. The cost, stated: two longswords are one base, so a sword slot fires whichever the pack lists first. Arbitrary rather than wrong, and right for the stacks the bar is mostly for | `item_bar.js` header |
| **Pressing a worn item says so rather than taking it off** | a weapon swap on the same key is a real design and a different one. Saying "already on your mainHand" is the version that cannot surprise you | `item_bar.js` `use` |
| **The gain shape, 0.25 in / 2.15 held / 0.6 out** | the brief gives three seconds and no shape. These three add to exactly three, and they are numbers rather than a CSS animation so node can measure them | `hud.js` `GAIN` |
| **The sort's shelf order** | the brief names weapons, shields, armour, jewellery, consumables, foods, materials, tools. Off hand items and instruments are named by neither, and sit after jewellery. Armour runs down the body in `items.SLOTS`' own order | `inventory.js` `sortRank` |
| **The sort's line says numbers, not a verb** | "sorted" is indistinguishable from a button that did nothing to a pack that was already tidy | `inventory.js` `sort` |

## 9. What was measured

Four suites, run on a quiet machine.

**`win_abilities.test.mjs`, 105 checks.** The book draws **78** cards for a
character with any skills at all. A fresh warrior (`OPENINGS_BY_ID.warrior`,
Swordsmanship 50, Tactics 50, Anatomy 30, Parrying 40, Healing 30) has **10**
unlocked, so **68** cards come back locked, and that 68 is asserted as
`ABILITIES.length - unlockedFor(...).length` rather than typed. Whirlwind at
Swordsmanship 33.4 reads exactly `Swordsmanship 50 and Tactics 40` as its
requirement and `unlocks at Swordsmanship 50, you are at 33.4, and Tactics 40,
you are at 0` as its locked line; the same row at Macefighting 41 names
Macefighting instead. `requirementView` agrees with `meetsRequirements` on all
78 rows driven both ways, at zero skills and at 100 in everything. The last
section builds the **real** panel against a fake document: firing `dragstart`
on Power Strike hands over exactly `{"ability":"powerStrike"}`, firing it on
Fireball hands over **nothing** and calls `preventDefault`, and firing it on

**`item_bar.test.mjs`, 94 checks.** A potion dropped into slot 0 and F5 pressed

itemBar` reads `f3,f6,f7,f8,f9,f10,f11,f12`, and W, `3`, F1, F2 and a key
another slot holds are each refused by name. The key guard is driven against a
fake window: F5 and F11 return `prevented === true`, F3 and `a` and
`ctrl+F5` return `false`, a rebind flips F3 to prevented and F5 to not in the

**`hud.test.mjs`, 144 checks** (was 105). The item row has exactly 8 cells,

## 10. What is NOT verified

- **Nothing here has been looked at.** No browser ran in this pass. Every claim
  about the two column grid, the 64 px tiles, the padlock, the rail between the
  two bars and where the ticker sits is a claim about CSS that has been parsed
  by nobody. Fable's screenshots are the first real test.
- **The twenty five marks have never been rasterised.** The paths are hand
  written SVG. A path with a bad arc flag draws a blob and the test, which
  checks that a drawing exists and is the right one, would still pass.
- **The item bar's drop target has never taken a real HTML5 drag.** The test
  fires a synthetic `drop` with a fake `dataTransfer`. Whether the HUD's item
  row is actually reachable with the codex open, at the codex's `min(72vh,
  760px)` height, is a layout question nobody has answered.
- **F12 was not tried in a real browser.** The claim that a page cannot prevent
  it is Chrome's documented behaviour, not something measured here.
- **`setTool` is not wired**, so a tool slot says which line is missing. That is
  the branch that ships unless main.js passes the hook.
- **The gains ticker's position was chosen against `#bw-bl`'s position in CSS**,
  not against a screenshot of a pickup label. `right: 14px; bottom: 96px` may
  still collide with something on a short screen.

## 11. Two things this found and did not fix

**`inventory.add` merges stacks across materials, and it is losing metal.**
`stackFor` matches on `baseFor(other)?.id === b.id` alone. Measured: a pack
holding 3 iron ingots (`material: 'iron'`, `label: 'Iron ingot'`), given 2
copper ingots, comes back as **one** stack of 5 reading `material: "iron"`.
Two copper ingots became iron in silence. `win_crafting.js`'s `answersTo` reads
`it.material`, so the forge then believes you have five iron. The one line fix
is a material check in `stackFor`, exactly the one `sortOrder` uses:

```js
if (baseFor(other)?.id === b.id && (other.material ?? null) === (item.material ?? null)) return i;
```

It is not made here because the brief scoped inventory.js to `sort()` alone and
that change moves behaviour every other suite in the repo depends on. `sort()`
is deliberately **stricter** than `add`: it will not merge across materials, so
the sort is right where the pickup is wrong. Fable owns the call.

**A tool in the pack and a tool you own are two records.** See section 7.
`state.tools` is a purchase record and the pack is loot, and nothing joins
them, so a looted pickaxe cannot be taken in hand by any path in the game
today.
