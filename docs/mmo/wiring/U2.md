## 1. What main.js must call

### 1.1 The frame rate on the badge

`createDev` takes three more things, all optional, all only read for the counts:

```js
const dev = createDev({ sc, camera, player, hud, runtime, state, monsters, floaters, loot });
```

`monsters`, `floaters` and `loot` are already in scope where `dev` is built.
Anything not handed over reads `null` in the stats, never a zero.

`dev.update(dt)` already runs every frame. It now also samples the counts, so
nothing else has to be called per frame. Once a second, hand them to the HUD:

```js
// in the frame loop, beside the other once a second work
devBadgeAt ??= 0;
if (now - devBadgeAt > 1000) { devBadgeAt = now; hud.setDev(dev.on, dev.stats); }
```

`dev.stats` is `null` while dev mode is off and the live object while it is on,
so the badge shows nothing rather than a frame rate from the last time F1 was
pressed. It is ONE object, rewritten in place, so holding a reference to it is
holding the live numbers. Its shape:

```js
{ fps, frameMs, draws, tris, monsters, chunks, floaters, sacks }
```

`fps` is a rolling one second average, not one frame's `1 / dt`. A stuttering
second of 50 frames at 200 fps and 75 at 100 reads 125 fps and 8 ms, which is
measured in `win_dev.test.mjs`; a one frame reading would have said 100.

`dev.liveStats` is the same object whether or not the mode is on, for anything
that wants the numbers regardless.

U1 owns the badge itself. U2 owns only the numbers.

`ctx.home` is read if present, as `{ x, z }`, for the Home row. Absent, Home is

## 2. The one line src/game/monsters.js needs

`spawnAt(id, x, z)` landed and works; the bench now also has **Spawn here x5**,
which is five `spawnAt` calls on a 3 m ring, and **Clear spawned**, which has
nothing to call. `despawn(key)` is private to `monsters.js`, and the dev spawns
are the ones whose key starts `dev:`. Next to `spawnAt`:

```js
/** Take away everything the dev bench spawned. Returns how many went. */
despawnDev() {
  let n = 0;
  for (const key of [...live.keys()]) if (key.startsWith('dev:')) { despawn(key); n++; }
  return n;
},
```

Until it lands, Clear spawned changes nothing, counts the `dev:` keyed monsters
through `all()` and says:

> 5 of the bench's monsters are standing and none were cleared:
> src/game/monsters.js has no despawnDev() yet. docs/mmo/wiring/U2.md has the
> one line it needs.

Both branches are tested. A kill is deliberately NOT used as a stand in: a kill
leaves a corpse, a sack and a dead list entry, and that is not the same thing as
taking a spawn away.

## 3. The pack is 40 slots

`03-ITEMS-LOOT.md` says "a pack has slots (starting 20)". The user asked for a
bigger one, so `PACK_SLOTS` is **40** in both `src/game/state.js` and
`src/game/inventory.js`, which are the only two places it is written.

**The migration is `state.hydrate`.** A save written at 20 says `slots: 20` and
carries twenty records; the existing clamp raises the floor to today's
`PACK_SLOTS`, the array is rebuilt at the new size and the records are copied at
their own indices. Nothing moves and nothing is lost. A save that already
carries more (a bag bought under `06-ECONOMY-UI.md`) keeps every slot it has, up
to the 200 the clamp allows.

`inventory.normalise` deliberately does NOT grow a pack. It repairs a document;
it does not migrate one, and a pack handed to it with a smaller slot count on
purpose is entitled to keep it. Every real path into the game goes through
`hydrate` (a save) or `creation.js` (a new character), and both give 40.

Measured, in `win_dev.test.mjs`:

- a 20 slot save with items at indices 0, 4, 8, 12 and 16 comes out with 40
  slots, all five items at the same indices, and 20 appended nulls
- a 64 slot save stays at 64, with the item in slot 63 still in slot 63
- a save claiming 4 slots is raised to 40; a save with no slot count is 40
- the weapon rack (18 weapons) now leaves 22 slots free where it left 2

## 4. What the bench gained

The panel opens on the live readout and then Travel, because those are the two
things you look at while you press everything else.

| row | what the button calls |
| --- | --- |
| the readout | `bench.readout(dt)` every frame, drawn four times a second |
| Go to x, z | the five warp calls, then `ctx.forage.update` |
| Home | the same, to `ctx.home` or the origin |
| Deeper / Out | `runtime.dungeonGo('down' / 'up')`, unchanged |
| Zones | `zoneSearch(runtime.field, here)`, then a warp per row |
| Sites | `runtime.sitesNear(x, z, 8000)`, grouped by kind, then teleport or enter |
| Recent | the last five places the bench moved you to, newest first |
| Roll 10 / 100 / 1000 | `loot_drops.rollFor(monster, { luck, seed })`, that many times |
| Drop 10 sacks | a real roll each, then `ctx.loot.drop(pos, { items, gold })` |
| Give all | `inventory.add` per rolled item, counting the refusals |
| inspect | `affixes.identify(item, 100, { scroll: true })` then `affixes.describe` |
| Spawn here x5 | five `monsters.spawnAt` on a 3 m ring |
| Clear spawned | `monsters.despawnDev()`, section 2 |

### 4.1 Travel says where you landed and what the ground is

Every warp ends with a line naming the spot and the biome, read from
`runtime.field.biomeAt`. Underground it says so. With no field wired it says
"The world field is not wired here, so the ground has no name" rather than
inventing a biome.

`PLACE_RADIUS` went from 6 km to 8 km. Measured at the origin on the real world
field: **221 sites** within 8 km against 119 within 6 km (70 hamlets, 41 ruins,
35 dungeons, 29 shrines, 20 towns, 20 camps, 6 caves), found in 8 ms cold and
1 ms warm. The list still keeps the nearest 12 of each kind and the group header
says how many it held back, so the extra two kilometres cost one sweep at open
time and no rows.

### 4.2 The zone hunt

There is no index of biomes anywhere. `field.sampleAt(x, z)` is the only thing
that knows what the ground is at a point, so the only honest way to find a
desert is to look for one. `zoneSearch` walks rings outward, `ZONE_STEP` (100 m)
apart close in and coarsening by a tenth of the radius further out, until every
biome `field.biomes` declares has been seen or `ZONE_MAX_R` (24 km) is reached.

Measured on the real field, seed 20260904:

- from the origin, all **8** biomes inside **600 m**, in **135 samples** and
  about **5 ms**: meadow 0 m, boreal 200, desert 200, mountain 200, snow 200,
  ocean 300, beach 400, sakura 600
- from four places thousands of metres apart, all 8 every time: 1331 m in 538
  samples, 900 m in 286, 700 m in 179, 800 m in 229
- the worst of the five was 538 samples

Every point the hunt returns is checked back through `field.sampleAt` in the
test, so a row that says "desert 200 m" is a place that really is desert. The
answer is cached until you move more than a metre or warp.

### 4.3 The loot lab, and the thing it found

Every item in the lab comes from `loot_drops.rollFor`, which is the join a kill
calls: `tableFor` turns the monster's words into item bases, `loot.js` shifts
the rarity weights by tier and rolls the gold. There is no second roller.

**The two rarity columns are not the same question, and that is a real finding.**
`loot.js` rolls a rarity and then picks a base off the monster's table.
`items.makeItem` hands the rarity back when the base cannot carry one, because
there is no such thing as a blue ingot. Roughly half a tier 5 monster's table is
materials, so a straight count of the items reads "60% common" against a weight
table that says a tier 5 kill cannot roll a common at all. Both are true about
different things, so the lab prints both and names the gap:

- **of the ones that can take a colour**, against `weightsFor(tier, luck)`
- **of all items**, with the count of materials that are always plain

Measured, 2000 rolls of every tier 5 monster, seed 99: 812 gear and 1188
materials; **0 common gear and 0 uncommon gear**, which is what the two row
shift means; rare 65.8% against 70.0%, epic 21.9% against 20.0%, mythic 8.5%
against 7.0%, legendary 3.8% against 3.0%. Every plain item in the pile is on a
base `takesRarity` says cannot be coloured. The other direction is checked too:
a tier 1 roll does leave commons, 480 of 683 gear.

Also measured: 1000 rolls account for exactly 1000 (the six counts plus the
kills that left nothing); every item came off that monster's own `tableFor`; the
gold stayed inside `loot.GOLD` for the tier; the same seed rolls the same
thousand and a different seed does not.

### 4.4 The sacks

Ten sacks land on two rings around you and each one holds at least one item. A
roll can come back with gold and nothing else, so each sack is re rolled up to
`SACK_TRIES` (12) times until it has something in it, and the line says how many
rolls it took. Measured: 10 sacks, the farthest **3.50 m** off, one item each,
gold 41 to 80 for a tier 3, every item off the monster's own table, all of them
put down at the height `runtime.heightAt` reported. The line reports the
distance it measured, not the radius it asked for.
