# S1: save slots, and the roster that picks between them

The user's words: "i click create new character and its not working, we need a
way to create and select existing saved characters."

Both halves are here. The button was broken for a reason worth writing down,
and the reason is the same reason there was nowhere to select a character from.

## The bug behind the button

`ui.js` gave the settings window this hook:

```js
newCharacter: () => { syncToCharacter(actor); state.clearSave?.(); location.reload(); },
```

It cleared the save and reloaded. `main.js` had this, from the day the loop was
written:

```js
window.addEventListener('pagehide', saveNow);
```

`location.reload()` fires `pagehide`. `saveNow` calls `state.save()`. The
document was still in memory, whole, so the save that had just been cleared was
written straight back before the page went, and the reload came up on exactly
the character the player had asked to be rid of. The button destroyed nothing
and did nothing, twice: it also armed and asked for a second press first, so
the player pressed it twice to get nothing.

That is the whole failure. It is not a missing `newCharacter`; it is two
correct pieces of code with no idea the other existed.

The fix is not to remove the pagehide save. It is that nothing needs wiping any
more, because there is somewhere else for a new character to go.

## One save became a shelf of them

| key | what is under it |
| --- | --- |
| `brackenwake-roster` | `{ v, slots: [row], lastPlayed }` |
| `brackenwake-save-v2:<id>` | one character document, the same shape as ever |
| `brackenwake-save-v2` | nothing, after the first boot. It was one document; it is now a prefix |
| `brackenwake-save-v1` | nothing, after the first boot |

A row:

```js
{ id, name, opening, createdAt, playedAt, needsCreation, summary }
```

`summary` is `summarise(document)`: the name, the opening and its word, the top
three skills with their values, the gold, where they stand and the position it
was worked out from, whether they were ever finished, and when. It is written
on **every** save of that document, so the roster screen never opens a document
to draw a card, and never shows a number a save ago.

Where they stand is `zoneAt(pos.x, pos.z)` from `src/world/zones.js`, the same
lookup the terrain uses to name ground. A card cannot claim a zone the player
was not standing in, and open ground has no zone, so the card says
`open country, at 812, -44` rather than inventing a name.

### The migration, and the order it happens in

`migrateLegacy(storage)` runs once, from `state.load()`, and only when the
roster has nobody in it.

1. Read `brackenwake-save-v2` as a **string**.
2. If that parses as an object, that string is what goes into the slot,
   character for character. If it does not, try `brackenwake-save-v1` and run
   it through the existing `migrateV1`, which is unchanged.
3. Write `brackenwake-save-v2:1`.
4. Read it back and compare it to what was written.
5. Write the roster.
6. **Only now** remove the old key.

Any step that fails leaves the old save exactly where it was: a write that does
not read back takes the half written slot out again; a roster that cannot be
written takes the document out again, because a document nothing lists is a
document nothing will ever open. The worst case is that the migration runs
again on the next boot.

Measured in `state.test.mjs`: the migrated document deep-equals the old one AND
is the same string; a storage that lies about what it read back leaves the old
save untouched and lists nobody; a storage that refuses the roster write does
the same.

### What changed for a v1 save

The v1 key used to survive until the first v2 save. It is now removed during
`load`, because the migration writes and verifies the new document before it
removes anything, which is a stronger guarantee than waiting. `state.test.mjs`
pins the new order by name.

## The API on `state`

```js
state.slot                       // which character is open, or null
state.roster()                   // every row, newest play first, `open` marked
state.openSlot(id)               // put that character in memory
state.newSlot()                  // a blank in a fresh slot, needsCreation true
state.deleteSlot(id, opts)       // row and document together
state.save()                     // writes ONE key, and the roster row with it
state.load()                     // migrate, then open: this slot, or lastPlayed, or the first
state.clearSave()                // this character off the shelf, and both legacy keys
```

`deleteSlot` refuses the slot that is open unless the caller passes
`{ evenIfOpen: true }`. The roster screen passes it, because no game is running
behind that screen; a running game never should.

`save()` writes exactly two keys, this slot's document and the roster, and the
test measures that by recording every key the storage was handed: saving slot 2
does not touch slot 1's key, and slot 1's stored bytes do not change.

A `createState` that was never given a slot takes the lowest free number on its
first save rather than dropping the write, which is what `shop.js` and every
older test get.

## The roster screen

`src/game/roster.js`:

```js
createRoster(hudRoot, { state, onPlay(slotId), onNew(), sc })
```

Full screen over the world that has already been raised, in the codex's own
furniture: dark parchment with the corner marks, gold rules under Cinzel small
caps, Cormorant for anything said in a sentence. One card per character with
the name, the opening, the three best skills, the purse, the ground they stand
on and when they were last played; a Play button, a small Delete that asks
twice the way the settings button used to; and one card for a new character.

Like `creation.js` it runs its own render loop over the scene, and like
`creation.js` it takes itself off the screen **before** it calls back.

- Arrows move between cards, Enter plays the one in hand, Escape does nothing.
  There is nothing behind this screen to go back to, and a key that looked like
  it closed the screen would close nothing.
- Arming a Delete puts that card in hand, so an arrow key takes the question
  back with it and Enter cannot play somebody else by mistake.
- Deleting the last character goes straight on to making somebody, because an
  empty roster is not a screen anyone can do anything with.
- The three marks on a card are checked against `ui_theme.ICONS` at load
  (`auditRosterIcons`), because `icon()` falls back to a cross without a word
  and three identical crosses would say nothing.

## The boot

```
world  ->  bootStage  ->  roster | creation | game
```

`bootStage(state, flags)` is exported from `main.js` and is pure:

| answer | when |
| --- | --- |
| `roster` | somebody has been made. Or the settings note, for a slot begun and never finished |
| `creation` | nobody made, and the document in hand asks to be made: a new install, and a v1 save that has just moved in |
| `game` | nothing to choose and nothing to make: a whole character in memory that no roster lists, which is a storage that refuses to be written |

All three are driven in `wiring.test.mjs` against a real `createState` over a
`Map`, and the fourth case (`bootStage(null)`) is driven too.

Each screen removes itself before the next goes up. `window.__bw` while the
roster is on the glass is `{ sc, state, hud, audio, input, camera, THREE,
roster: true }`, which is what the creation gate exposes with `roster` in place
of `creating`. The watchdog in `index.html` waits for `window.__bw` and is
satisfied by all three.

### A note on the two readings of "when does the roster show"

The brief said both "whenever at least one slot exists" and "a flag that makes
the roster show even if only one slot exists". Those cannot both be the rule.
What is built is the first one: the roster is the front door whenever there is
somebody to choose, one character or five, because that is where Delete lives
and a player who wants a second character should not have to find a setting to
get there. The flag still does real work, and this is the only thing it does:
it forces the roster for a slot that was **begun and never finished**, which
the default rule sends to the creation screen instead. Both are tested.

## The settings button now

`win_settings.js`, under a header that reads Characters rather than Start
again:

> **Another character**
> this one is saved first, and the roster is where you make a new one or take
> up an old one
> `[ Save and go to the character roster ]`

One press. No arming, and nothing about wiping, because nothing is wiped. The
hook is still `ctx.newCharacter`, and `ui.js` fills it in with

```js
newCharacter: () => { syncToCharacter(actor); toRoster(state); },
```

`toRoster(state)` lives in `state.js`: it saves the open slot, leaves the note
in `sessionStorage` under `brackenwake-show-roster`, and reloads. The roster
takes the note down the moment it is on screen; when the answer is any other
screen `main.js` takes it down instead, so a note nobody can act on cannot
follow the player around the session.

The pagehide save still fires on that reload, and now it writes the same slot
the button just wrote. That is a save happening twice, which is nothing.

## Verified

Every number below was run, not estimated.

| suite | before | after |
| --- | --- | --- |
| `state.test.mjs` | 205 | 278 |
| `roster.test.mjs` | did not exist | 76 |
| `wiring.test.mjs` | 160 | 178 |
| `win_settings.test.mjs` | 48 | 50 |

`npm test`: all suites green. `npx vite build`: clean, 125 modules.

No test in this work touches `localStorage` or `sessionStorage`. Every store is
a `Map` behind `getItem`, `setItem` and `removeItem`, and `roster.test.mjs`
asserts at the end that `localStorage` was never even defined in its process.
The user's own save was never opened, read or written.

`roster.test.mjs` drives the real panel against the fake document
`win_bag.test.mjs` uses, and the real `createState` over a `Map`: N cards for
N slots at N of 1, 2 and 3; Play on each of three cards hands back that card's
id and the id is one `state.openSlot` accepts; Delete needs two presses, and
after the second the document key is gone as well as the row; New calls `onNew`
and nothing else; the arrow keys and Enter go through the same `keydown`
handler the window was given, and after the screen leaves, that listener is off
the window.

## Not verified

Nothing here was opened in a browser. The roster's look, the turning world
behind it, and the fonts are unverified: they are the same tokens, the same
`injectTheme` and the same shape of CSS `creation.js` uses, but that is an
argument, not a measurement. Whether the scene renders sensibly behind the
roster is also unmeasured; the screen calls `sc.render()` itself the way
`creation.js` does, with none of the world system's own render pass, so the
water and the sky may not be doing what they do in game.
