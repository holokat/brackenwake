# W2: combat, monsters, loot bags, placeholder bodies

Four files, one job: the thing in front of you is alive, it fights back, and
when it stops it leaves something on the grass.

| file | what it is |
| --- | --- |
| `src/game/combat.js` | the old hunting resolver, unchanged, plus `createCombat` under it |
| `src/game/monsters.js` | spawning, the AI, and the bodies that carry it |
| `src/game/monster_models.js` | box rigs, one silhouette per kind, coloured by tier |
| `src/game/loot_drops.js` | the sack on the ground for 90 s, and the monster-word to item-base join |

Tests: `combat.test.mjs` (167), `monsters.test.mjs` (113),
`loot_drops.test.mjs` (54). `npm test` is green across the whole tree.
Nothing in `src/mmo/` was edited.

## Creating them, in this order

`loot` before `monsters`, because a monster's death asks the loot for a sack.
`combat` before `monsters`, because `createMonsters` subscribes to
`combat.onDeath` at construction. Everything else is free.

```js
import { createCombat } from './combat.js';
import { createLootDrops } from './loot_drops.js';
import { createMonsters } from './monsters.js';
import { spawnMonster } from './actor.js';          // W1

const combat = createCombat({ floaters, hud, audio, progression, rng: Math.random });
const loot   = createLootDrops(sc, { floaters, hud, audio });
const monsters = createMonsters(sc, runtime, {
  actorFactory: spawnMonster,      // W1's. Without it monsters.js uses its own
                                   // stand-in, makeMonsterActor, which is for
                                   // the tests and not for the game.
  combat, loot, floaters, hud, audio,
  rng: Math.random,
  deadUntil: character.deadUntil,  // the character document's own array, mutated in place
  spawnPoint: { x: startX, z: startZ },   // 60 m of quiet around it
});
```

### The actorFactory call, exactly

```js
actorFactory(id, { pos: { x, y, z }, key, row, rec })
```

`id` is a key of `src/mmo/monsters.js` `MONSTERS`; `row` is that record; `key`
is the spawn slot's stable id (`"12,7:skeleton:1"`), which is also what goes
into `deadUntil`. It must return an actor of the 07 shape. `monsters.js` then
fills in, **only where the factory left them undefined**: `temperament`,
`family`, `run`, `tier`, `ai.aggro`, `ai.leash`. It always sets `ai.home`,
`ai.state`, `ai.target`, `radius` and `pos`, because those are the runtime's and
not the actor builder's.

One thing the builder has to get right, whoever writes it: `combat_rules.js`
must read back the row's own numbers. `attackSkill(actor)` has to come out as
the tabled `hit` and `defenceSkill(actor)` as the tabled `def`, which means the
leftover goes into `bonuses.defence` once the weapon skill and Parrying have
taken their halves, and only the rows whose notes say so carry Parrying and a
shield. `monsters.test.mjs` drives all forty-one rows through those two readers;
if W1's builder does it another way, that test will say which rows and by how
much.

If W1's `spawnMonster` takes different arguments, say so and I will match it;
nothing else about the wiring changes.

### progression

`combat.js` calls, and only for an actor whose `kind` is `'player'`:

```js
progression.lesson(actor, skillId, difficulty, success)
progression.statLesson(actor, statId, difficulty, success)
```

It passes the **actor**, not the character document. If W1's progression wants
the document, main.js should hand `createCombat` a thin adapter rather than
either of us changing shape. Monsters are never taught: a skeleton has no
document, and `rollGain` would happily invent one.

## The frame

07's order, with the two new lines in place:

```
input.beginFrame
intent -> player.update -> actor.pos
  if (player.landed) combat.applyFall(playerActor, player.landed.fallMetres, now)
camera.update
runtime.update(dt, now, x, z, dayFactor)
monsters.update(dt, now, playerActor, night)     <-- aggro, walk, queue swings
combat.update(dt, now)                           <-- resolve, apply, tick, deaths
abilities.update(dt)
loot.update(dt)                                  <-- bob, fade, expire at 90 s
floaters.update(dt)
hud.update
sc.setDay, sc.follow, render
input.endFrame
```

`monsters.update` must come **before** `combat.update`: it queues the swings
that `combat.update` then resolves in the same frame. `loot.update` may go
anywhere after `combat.update`; next to the floaters is tidiest.

`night` is the same flag `runtime`/`fauna` already use (`sc.dayFactor(now)`
below its night threshold). Day and night are different rosters and the sweep
re-rolls the near ring the moment it flips.

## Events main.js has to route

### 1. The player clicks a monster

`interact.js` (not mine) already asks `runtime.pick` and `pickTarget` and picks
the nearer of a tree and an animal. A monster is a third candidate:

```js
const mon = monsters.pick(raycaster);         // the monster record, or null
if (mon) {
  const r = combat.queueSwing(playerActor, mon.actor, { now });
  if (!r.queued && r.reason === 'out_of_reach') hud.log(`${mon.name} is ${Math.round(r.dist)} m off`);
  // 'cooldown' says nothing, the same rule interact.js already uses for a chop
}
```

`mon` carries `{ key, actor, model, row, name, id }`. For the hover line and the
target frame, `mon.name` and `mon.actor.health / maxHealth`.

Precedence: a monster should beat a tree and an animal when it is nearer the
cursor, on exactly the rule `interact.js` uses now.

### 2. The swing key

Whatever key or button an ordinary swing is bound to:

```js
const target = currentTarget || monsters.nearestHostile(playerActor.pos, playerActor.yaw, 3, Math.PI / 3);
if (target) combat.queueSwing(playerActor, target.actor ?? target, { now, jumpAttack: player.airborne });
```

`jumpAttack` is 02-COMBAT's +25%, and `combat.js` reads it straight through to
`resolveMelee`.

### 3. Landing

`player.update` sets `s.landed = { fallMetres }` for exactly one frame:

```js
if (player.landed) combat.applyFall(playerActor, player.landed.fallMetres, now);
```

Free under 4 m and silent, because nothing happened. Over it, an orange number
and a line. `(metres - 4) * 6`, and nothing resists it.

### 4. Death

```js
combat.onDeath((actor, killer) => {
  if (actor === playerActor) startDeathScreen();      // 5 s, then a shrine, W5's
  // monsters.js is already subscribed and handles its own: the sack, the
  // topple, and the deadUntil entry. main.js does not need to do it again.
});
```

The player's respawn should call `combat.clear()` and
`monsters.rescan(x, z, night)` after the teleport, so nothing is still swinging
at a body that has moved 400 m.

### 5. Taking a sack

```js
const bag = loot.pick(raycaster) || loot.nearest(playerActor.pos, 3);
if (bag) loot.take(bag, (items, gold) => inventory.takeAll(items, gold));
```

The handler returns what it **accepted**: `undefined` for everything,
`false` for nothing, or `{ items: [...], gold: n }` for a part of it. What it
refused stays in the sack and the player is told, in the same line, both halves.
W3's `inventory.js` should return the partial shape.

### 6. Saving

`monsters.js` writes into `character.deadUntil` in place: entries are
`{ key, id, until }` with `until` a **wall clock** epoch in ms (`Date.now()`),
not the frame clock, so a camp cleared before a reload is still clear after it.
Nothing else needs doing; whoever saves the character saves the list.

## Decisions taken, and the ones worth arguing with

**Spawn density.** 05 gives it as a distance ("one per 150 m of wild land at
night, one per 400 m by day") and never mentions a chunk. Read here as: a chunk
is 64 m across, so the chance it holds a group is `64 / 150` at night and
`64 / 400` by day. That is `GROUP_CHANCE` in `monsters.js`, measured in the test
at 43.5% and 17.3% over 1,681 chunks. If the intended reading is different, this
is the one constant to change.

**Where a monster comes from.** The biome's HABITAT row, except inside a ruin's
or a cave's ground, which use their own rows: 05 says of ruins "always
something", and a skeleton in a ruin standing in a meadow should be a skeleton.

**The loot join.** `monsters.js` writes loot tables in words (`bone`, `helm`,
`tunic`); `items.js` has bases (`leather_head`, `chain_chest`). Fifteen of those
words name nothing, and `loot.rollDrop` **throws** on the first one. Neither
pure file may be edited and both are right, so `loot_drops.js` translates:
armour words take the material of the monster's tier (cloth 1, leather 2,
studded 3, ring 4, chain 5, plate for a boss), `wood` is a log, `meat` is food,
`bone` is a reagent (05: the necromancer "sells bone reagents"). Four words have
no honest base yet, `hide`, `thickHide`, `scaledHide` and `scroll`, and they are
dropped from the table rather than turned into something they are not: hides are
Skinning's, and Skinning is nobody's yet. `auditLootTables()` runs at load and
throws if that ever leaves a monster with an empty table.

**A bleed's rate.** Poison has a rule and goes through `poisonTick`. A bleed
does not: 04 writes Rend as "bleed 3 a second for 8 s", an absolute rate. So
`applyStatus(actor, 'bleed', { perSecond, seconds })` is the real call, and
`BLEED_PER_LEVEL = 2` is only the fallback for a bleed given as a bare level.

**Swings an ability asks for.** `abilities_runtime.js` sends `multiplier`,
`hitBonus`, `ignoreARFraction`, `jumpAttack`, `shots` and `immediate` with a
swing. All of them are read: `hitBonus` and `ignoreARFraction` are folded into a
shallow copy of the attacker under the names `combat_rules.js` already uses
(`bonuses.hit`, `bonuses.armourPiercing`), and `multiplier` is put through
`combat_rules.damage` with the same roll and the same crit. `immediate` skips
the cooldown gate and does not start it, so a three shot ability fires three
times without also costing the ordinary swing. Measured both ways in
`combat.test.mjs`.

**32 m does not quite kill a fresh warrior.** 02 says it does; its own formula
says `(32 - 4) * 6 = 168` against 170 health. The formula wins, and 33 m is the
drop that actually does it. The test says so out loud rather than papering over
it.

## Not done, and named so nobody assumes otherwise

- **Underground.** `HABITAT` has `dungeon1`, `dungeon2`, `dungeon3` and `cave`
  rosters, and nothing spawns into them. `monsters.update` despawns everything
  and switches the layer off while `runtime.inDungeon`, because the overworld
  monsters are standing at coordinates directly over your head. Dungeon
  placement needs the level layout and is a separate job.
- **Ranged and casting monsters.** Goblin scouts throw knives, cultists cast
  Fireball, wyverns breathe. The AI walks into melee reach and swings; the notes
  that say otherwise are read for poison only. `combat.queueSpell` exists and
  works, so a caster AI is a small addition on top, not a rewrite.
- **Flying.** Bats, harpies, wyverns and the bone dragon walk on the ground.
- **Bosses, phases, group buffs.** `BOSS_PHASES` is untouched; a war cry buffs
  nobody.
- **Skinning.** Which is why hides have no item base and no bag carries one.
- **The glb models.** `buildMonsterModel(id)` returns
  `{ group, parts, radius, height, shape, setAnim, update, anim, dieDone,
  dispose }`. W6 replaces the insides and nothing outside this file changes.
  Six silhouettes are authored by hand (rat, skeleton, wolf, goblin, zombie,
  spider); the other thirty-five monsters fall back to the shape their family
  suggests, and `auditMonsterShapes()` throws at load if a monster has none.
