> Wood and logs and ingots should be different types. Depending on the wood, we

## 1. The reason this was worth doing, measured

Before this change, of the 48 different materials the 486 recipes in
`recipes.js` ask for, **23 could not be paid at all**. Ten of them were metals
and four were woods:

```
ash, cloth, coldiron, copper, emberite, heartwood, iron, ironbark, oak,
rimesteel, silver, starfall, tin, verdite, voidrock,
bloodmoss, brownCap, garlic, ginseng, mandrake, nightshade, paleCap, wildBerries
```

That is measured, not reasoned: `git archive HEAD` into a scratch tree, then
every recipe's material list run against every stackable base's `material` tag.

The cause was the three stacks themselves. `{ id: 'ingot', name: 'Ingot',
weight: 1 }` carries no `material`, and `win_crafting.answersTo` matches on
`it.material || it.base || baseFor(it).material`. So a pack holding twenty
ingots answered to nothing, and **every metal recipe in the game was unmakeable
and nobody had counted it.** The same for `log` against `oak`.

After: **9 unpayable, and not one of them is a wood or a metal.**

```
bloodmoss, brownCap, cloth, garlic, ginseng, mandrake, nightshade,
paleCap, wildBerries
```

Those are the eight alchemy herbs, which have no base anywhere, and `cloth`,
which resolves only to the six armour bases whose tier material is cloth and
therefore is not a spendable stack. Both are outside this brief and both are
written down in section 6 rather than quietly closed.

## 2. The three families

Built from `ores.js`, which is the one table that says what the metals and the
woods are. Nothing about which metals or which woods exist is invented here.

### Fourteen woods

Eleven are grown by the forest, in `flora.js` ALL_KINDS's own list. Three are
`ores.js` WOODS with no tree in this world yet, and they carry `grown: false`
so they cannot be mistaken for something you could go and chop.

| base | name | material | grown |
| --- | --- | --- | --- |
| `oak_log` | Oak Log | `oak` | yes |
| `birch_log` | Birch Log | `birch` | yes |
| `beech_log` | Beech Log | `beech` | yes |
| `fir_log` | Fir Log | `fir` | yes |
| `spruce_log` | Spruce Log | `spruce` | yes |
| `pine_log` | Pine Log | `pine` | yes |
| `sakura_log` | Sakura Log | `sakura` | yes |
| `willow_log` | Willow Log | `willow` | yes |
| `palm_log` | Palm Log | `palm` | yes |
| `deadwood` | Deadwood | `dead` | yes |
| `cactus_wood` | Cactus Wood | `cactus` | yes |
| `ash_log` | Ash Log | `ash` | no |
| `heartwood_log` | Heartwood Log | `heartwood` | no |
| `ironbark_log` | Ironbark Log | `ironbark` | no |

Deadwood and Cactus Wood are not called logs, because neither of them is one.
Their `material` stays the flora kind (`dead`, `cactus`), which is the word
`interact.js` reads off the field it just felled.

A log weighs two stones, which is what the old `log` stack weighed.

### Ten ores, ten ingots

One ore per `ores.js` tier (`copper_ore` ... `starfall_ore`) and one ingot per
`ores.js` METALS row, which is every ore that forges something plus the Bronze
alloy. **Tin has an ore and no ingot**, because `ores.js` says so out loud:
"tin alone forges nothing; it becomes bronze". A recipe asking for tin is paid
in Tin Ore.

An ore and its ingot **deliberately carry the same word**. `iron_ore` and
`iron_ingot` are both `material: 'iron'`, so a smith may pay in either. Nothing
in `recipes.js` smelts ore into an ingot today, so a rule that only ingots count
would have left every metal recipe exactly as unpayable as it already was. The
uniqueness check in `auditMaterialBases` is therefore per family, and it says so
in a comment rather than being a hole.

## 3. The three dead ids

`log`, `ore` and `ingot` are gone from `BASES` and live in `BASE_ALIASES`:

```js
export const BASE_ALIASES = { log: 'oak_log', ore: 'copper_ore', ingot: 'iron_ingot' };
```

`baseFor` resolves them and warns **once per id for the life of the process**,
naming the file and line that asked:

```
[items] "ingot" is no longer a base. It resolves to "iron_ingot";
        the caller at file:///.../src/game/win_talk.js:708:11
        should name the material it means.
```

That warning is the point. It is a to-do list that writes itself, and it is how
`win_talk.js` and `openings.js` were found rather than guessed at.

`baseForQuiet` is the same lookup with the warning off, because an audit that
spent the one warning at import would leave every real caller silent. That is
what `auditMaterialBases` uses, and the test proves the difference both ways:

```
ok   baseFor("log") resolves to an oak log
ok   and it warned exactly once
ok   and the warning names the caller, not this module
ok   the second, third and fourth time it says nothing   1 warning(s)
ok   baseForQuiet reaches the same base
ok   and adds no warning at all
```

`auditItems.materials.aliases` lists all three. `aliasesUsed()` says which have
actually been asked for this session, and it is `[]` at load, which is checked.

**A save from before this change is safe on both paths.** A v1 save's `wood: 37`
migrates through `MATERIAL_BASE.wood` into a stack of 37 Oak Logs. A v2 save
holding a stack literally called `log` goes through `hydrateItem`, which already
writes `base: b.id` off `baseOf`, so nine logs become nine Oak Logs and the HUD
goes on counting them. Both are driven in `state.test.mjs`:

```
ok   the nine logs become nine oak logs and are still counted as wood   oak_logx9 copper_orex4 iron_ingotx2 stonex3
ok   the two ingots become iron ingots, which the HUD never counted and still does not
ok   and a base nothing has ever heard of is still dropped rather than carried as a hole
```

## 4. The legacy view: three numbers over twenty five stacks

The HUD still draws wood, stone and ore. Underneath:

```js
MATERIAL_STACKS = { wood: LOG_BASES (14), stone: ['stone'], ore: ORE_BASES (10) }
MATERIAL_BASE   = { wood: 'oak_log', stone: 'stone', ore: 'copper_ore' }
```

- `state.materials.wood` is the **sum** of all fourteen woods. An oak, a birch
  and a palm read as one number and sell as one lot.
- `state.addMaterial(baseId, n)` is the species aware write, and `interact.js`
  is the caller that uses it. It returns `{ added, dropped, base, material }`,
  so a caller that says "four logs" can also say which.
- `state.add('wood', n)` is kept for every caller with no species to offer, and
  opens a stack of oak. Oak is the tier 1 wood in `ores.js` and the commonest
  tree in the meadow a settler starts in.
- **the cap is the family's, not the stack's.** A hundred oak and a hundred
  birch is a hundred and fifty of wood, and the other fifty comes back:
  `{"added":50,"dropped":50}`, measured.
- `state.take('wood', n)` drains **every** species in pack order and reports
  `by`: taking eight from four oak, three birch and two palm returns
  `{"oak_log":4,"birch_log":3,"palm_log":1}`.

`auditState` now also proves every counted stack is real and stacks, that no
stack is counted by two counters (which would double a HUD number), and that
each stack joins back to the counter that counts it. Driven the other way too:
`materialFamilyOf('longsword')` is null.

### The shop needs no line

`shop.js` reads `state.materials[m]` and calls `state.take(m, n)`, and both of
those now cover every species. **Selling wood sells the birch as well as the
oak with no edit at all**, and `shop.test.mjs` is green untouched (93 checks).
There is one wrinkle and it is in section 6: that market pays one flat price per
family, so a Starfall Ore sold through it fetches the same 9 as a Copper Ore.
The town market in `win_talk.js` prices every base separately and does not have
this problem.

## 5. The wood on the ground

### What the axe does now

A felled tree no longer teleports a number into the pack. `interact.js` calls

```js
loot.drop(stump, { items: [makeItem({ base: '<species>_log', count: n })], gold: 0 })
```

and says what is lying there:

```
the oak comes down and leaves four oak logs
the ore seam breaks open and leaves two copper ore
```

**Stone does not do this.** A boulder is quarried away rather than felled, there
is nothing left standing to leave a bag beside, and a pickaxe that put a sack on
the ground every time you tapped a rock would be a worse game. Stone goes
straight into the pack in exactly the words it always did.

### The join is the field's NAME, not its species

`flora.js` builds every stand as `world:<kind>` and a cave builds
`dungeon:<id>:<level>:ore`. The last segment is the kind, which is the same read
`nounFor` has always done. It is **not** `field.species`, which is the Arbor
recipe and says `spruce` for a fir; using it would have made every fir drop
spruce logs and nothing would have looked broken.

`auditHarvestDrops()` runs at module load next to `auditLootCarry`, and is
driven both ways: every kind in `GROWN_KINDS` has a real log that counts as wood
in the pack, and every tree word in `NOUNS` either has one or is on `NO_LOG`
(`kapok`, `fig`, `trees`, `woods`, `rock`, `boulders`, `ore`) and really has
none. `interact.test.mjs` then checks `GROWN_KINDS` against `flora.js`
ALL_KINDS in both directions, so a twelfth species cannot ship with no log and a
log cannot ship for a tree nothing grows.

All eleven felled for real, through `interact.act` with real fields and a real
`chopTree`:

```
oak->oak_log beech->beech_log birch->birch_log pine->pine_log spruce->spruce_log
fir->fir_log willow->willow_log palm->palm_log sakura->sakura_log
dead->deadwood cactus->cactus_wood
```

and for every one of them the pack did not move and the bag landed at the tree's
own `x`, `gy`, `z` rather than at the player.

### How `interact.js` finds the loot layer with no edit to `main.js`

`main.js` builds `createInteract({ sc, runtime, player, state, hud, input, audio,
progression })` and does not pass `loot`, and `main.js` is not this agent's
file. Three ways in, tried in order:

1. the `loot` argument, which `createInteract` now takes. **This is the wiring
   `main.js` should use**, and it is one word (section 7a).
2. `runtime.loot`, if a runtime ever carries one.
3. `currentDrops()`, a module level registry in `loot_drops.js` set by
   `createLootDrops` and cleared by `dispose()`. There is exactly one loot layer
   in a running game, the same way `tree_edit.js` keeps exactly one list of
   fields, and this is what makes the axe really leave wood on the ground today
   rather than leaving a to-do in a document.

Driven in the test with no `loot` argument at all: an interactor built the way
`main.js` builds it fells a birch and the live layer has the bag.

**And if there is no loot layer anywhere**, the wood goes into the pack as its
own species and the line says so:

```
the willow comes down, three willow logs into the pack
```

A swing that quietly produced nothing is the one outcome that must never happen,
so that branch is driven too, with a layer that refuses every drop.

### Picking it up

Nothing new. `main.js` already has `loot.nearest(player.pos, 3)` on E and
`loot.pick(ray)` on a click, and both go through `loot.take`, which hands the
contents to the pack and keeps what the pack refused. The whole path is driven
end to end in `interact.test.mjs`: chop a birch, look at what is lying there,
take it, and the pack has birch in it.

```
ok   what is lying there is birch   birch_logx2
ok   it is a woodpile, not a sack   logs:birch
ok   and the cursor calls it what it is, with no sack in the sentence   two birch logs
ok   it sits where the tree stood   12, 0
ok   the pack is untouched while it lies there
ok   and the pack has the birch now   0 then 2
ok   the sack says what went in, in the words the axe used   two birch logs in the pack
```

### What it looks like

`shapeOf` grew two answers. A bag of nothing but one wood is `logs:<wood>`, a
bag of nothing but one vein is `ore:<vein>`, and **anything else is still a
sack**, driven four ways: a log with a sword in it, a log with money in it (coins
do not lie loose in a woodpile), two different woods in one bag, and a log with
an ore in it.

`lookOf` is new and is the reason a pile that gave up half its logs really
changes. `shapeOf` answers "sack or pile"; `lookOf` answers "does the picture
have to change", and it carries the drawn count. Without it a pile of five fir
that gave up three would have gone on showing five, which is the bug the test
caught:

```
ok   a pack that takes one stack leaves the other
ok   and what is left is still a woodpile, rebuilt in place   logs:fir, 2 logs
```

A woodpile does not turn, for the same reason a pile of gold does not: wood on
the ground is not a pickup icon. Measured, and it still expires at ninety
seconds with the last ten fading (opacity 0.50 at 85 s, gone at 90 s, and the
scene is empty after `dispose`).

### The words

Logs, ore and ingots are the stacks a player is told about by the handful, so
they are the ones that get the spoken number and the plural. Everything else
keeps the shape it had.

```
four oak logs          an oak log             seven iron ingots
20 iron ingots         three copper ore       some copper ore
three deadwood
```

Past twelve the digits are easier to read than the words. Ore and anything
ending in "wood" are mass nouns, so one lump is "some copper ore" and three are
"three copper ore", never "three copper ores". `labelFor` on a woodpile is
`four oak logs` with **no "a sack:" in front of it**, because what is lying
there is not a sack.

## 6. `log_piles.js`

Built the way `gold_piles.js` builds a purse, and for the same reasons.

**`buildLogPile(species, count)`.** One to six cut logs stacked in the
three-two-one pyramid that timber actually settles into, rows at the hexagonal
packing height so the top log rests in the groove rather than floating over it.
Each log is an open cylinder of `LOG_SEG` (12) segments with a disc closing each
end, merged into ONE geometry with ONE material, so a pile is one draw call.

Counted, not estimated: 4 x segments per log.

| logs | triangles |
| --- | --- |
| 1 | 48 |
| 3 | 144 |
| 6 | **288** |

288 is the worst pile in the game, against a `MAX_TRIS` of 1,500. A full pile is
86 cm long and 47 cm high, the bottom row rests at 8.5 cm which is exactly the
log's own radius, and no vertex of any of the fourteen woods reaches below 0 mm.

Bark is a `color` attribute rather than a texture, so nothing is loaded, decoded
or cached, and the species reads from ten metres:

- `plain` lengthwise grain, darker in the grooves
- `birch` near white with the short dark dashes birch bark has
- `ringed` the stacked collars of a palm
- `blossom` the grey with pink in it a cherry trunk has
- `succulent` a cactus, which is ribbed and green and not really a log

Measured mean vertex colour over a six log pile: birch 0.80 red against oak's
0.41, oak warm (0.41 red, 0.27 green, 0.12 blue), cactus green (0.48 green
against 0.33 red). The sawn end is a different colour from the bark on all
fourteen, and paler on thirteen; **birch is the one that is not**, because birch
bark is the white part of a birch. That is driven both ways rather than being an
exception hidden in a comment.

**`buildOreHeap(oreId, count)`.** One to six icosahedral chunks, 20 triangles
each, 120 at six. An icosahedron is unindexed, so three consecutive vertices are
one face and a face either carries ore or it does not: the result is host rock
with flecks in it, which is what a broken seam looks like and what makes a
voidrock heap read differently from a silver one without either being a solid
lump of metal. An emberite heap at six chunks measures 46 ore faces to 74 rock
faces.

`ORE_WORD` keeps each hex **next to the word in `ores.js` it is a reading of**
("warm brown", "blue black", "grey with a white flash"), because those hexes are
authored and somebody will disagree with one of them.

`auditLogPiles()` runs at load over every wood and every vein at every count
from 1 to 8, and is driven the other way as well: a wood that does not exist and
a vein that does not exist both build **nothing**, rather than a grey box.

```js
// src/game/win_crafting.js:279
const base = CRAFT_MATERIALS[id]?.kind === 'metal' ? 'ingot'
  : CRAFT_MATERIALS[id]?.kind === 'wood' ? 'log' : ...
```

This works: the alias resolves and the stamped `item.material` wins, so a

### 7d. `shop.js` pays one price per family

`shop.js` `sellPrice(m)` is `GOODS[m].sell`, one number for all wood and one for
all ore, so a Starfall Ore fetches the same 9 as a Copper Ore. The town market
in `win_talk.js` prices every base separately (`basePriceOf('starfall_ingot')`
is 11 and `basePriceOf('copper_ore')` is 1) and does not have this problem. If
the three-lot market is meant to stay, the fix is one line in `sell`: price the
lot out of `by`, which `state.take` already returns per base. `shop.js` is not
this agent's file and was not touched.

### 7e. The gaps this change did not close

- **the eight alchemy herbs.** `ginseng`, `garlic`, `wildBerries`, `bloodmoss`,
  `mandrake`, `brownCap`, `paleCap` and `nightshade` are asked for by recipes
  and have no base anywhere. Not wood and not metal, so out of this brief, but
  they are the last unpayable materials in the game.
- **`cloth`.** It resolves only to the six cloth armour bases, whose `material`
  is `cloth` but whose kind is `armour`, so `isIngredient` refuses them. A
  `cloth` stack would close it.
- **an ore seam has no tier.** Neither `flora.js` nor `dungeon.js` puts an ore
  id on a rock field, so **every seam in the game today gives copper**.
  `oreBaseFor` reads `field.oreId` when there is one, and `ores.js` `veinsFor`
  already knows which veins a biome and a depth can hold, so the fix is for
  whoever owns those two files to set `oreId` when the field is built. That is
  a real gap and it is deliberately not guessed at here.
- **`hydrateItem` drops `item.material` and `item.label`.** A crafted stack
  stamped Copper Ingot loses both on reload. That predates this change and it
  now matters less, because the base itself carries the material; a copper ingot
  saved as `copper_ingot` comes back as copper.

## 9. Suites failing on this working tree for reasons that are not this change

`win_map`, `fauna`, `roads`, `sitegrid`, `grass` and two site-hunt checks in
`win_dev` were red while this was written. **None of them imports `items.js`,
`state.js`, `interact.js`, `loot_drops.js` or `log_piles.js`**, checked by grep
