`src/game/gear_visuals.js` (new), their two `*.test.mjs`, `src/game/player.js`,

## The rig contract, as built

```js
rig = {
  group,                         // feet at y = 0, faces +z, 1.80 m unscaled
  parts: {
    hips, torso, head,
    armL, armR, handL, handR,    // handL/handR are Object3D at y = -0.62 in the arm
    legL, legR, footL, footR,    // footL IS bootL, one object under two names
    back,                        // on the torso at (0, 0.42, -0.11)
    shinL, shinR, bootL, bootR,  // the joints the gait solves for, unchanged
  },
  setAnim(name), update(dt, speedMps), setAppearance(a), dispose(),
  grip,                          // written by dressRig, read by the pose
  appearance, state, triangles,
}
```

`handL` and `handR` sit at exactly the point `effects.js` already reads a
caster's hand from (`const HAND = new THREE.Vector3(0, -0.62, 0)`). If either
moves, both move. `BODY.HAND_Y` is that number, exported so nobody has to
retype it.

`rig.update(dt, speedMps)` is for anything driven by ground speed rather than
by the controller: NPCs, and V5's monsters. The player still goes through
`createPlayer(...).update(dt, move, heightAt)`, which is unchanged apart from
easing `grip` into the pose.

## 1. `main.js`: three calls

### At boot, after `createPlayer`

```js
import { dressRig } from './gear_visuals.js';

const player = createPlayer(sc.scene, character.appearance);   // <- second argument
```

`character.appearance` is the record `openings.js` validates. Passing
`undefined` (an old save with no appearance) is safe: the rig falls back to the
house default, exactly the body that shipped before.

Then, once `inventory` exists:

```js
let rangedDrawn = false;                       // whatever the ability layer calls it
const dress = () => dressRig(player, character.equipment, { ranged: rangedDrawn });
dress();
```

`dressRig` takes `player` itself: it only wants `.parts`, and writing `.grip`
onto the api object is what makes `poseCharacter` close the hands.

### On every equipment change

`createInventory` already fires `onChange(character, what)`. One line:

```js
const inventory = createInventory({
  character, actor, recompute,
  onChange: (c, what) => {
    state.touch(what);
    if (what === 'equipment') dress();          // <- the whole wiring
  },
  ...
});
```

`dressRig` is idempotent and diffs against what is already on the rig, so
calling it on every change (or every frame, if that is ever easier) costs
nothing: 200 no-op calls measured at 4 ms, 0.02 ms each. A full change of kit
measured at 1 to 2 ms.

### When the ranged set toggles

Wherever the game decides the bow is up (G2's `abilities_runtime`, or a key):

```js
rangedDrawn = true;  dress();     // bow into the hands, sword to the hip
rangedDrawn = false; dress();     // bow back onto the shoulder blades
```

That is the only thing `opts.ranged` does. With it false the ranged item hangs
on `back` and the melee weapon is in `handR`; with it true they swap, the
off-hand shield is put away, and `rig.grip` becomes `'bow'`.

### Nothing else

`effects.js` needs no change. `dressRig` never touches the channels effects
owns, and the gear is parented to anchors the swing and cast clips already
rotate, so a sword swings with the arm because it is a child of the arm.

## 2. `creation.js`: pass the look to the preview

Line 708 currently builds a rig with no appearance and scales it by hand:

```js
rig = buildCharacter();
rig.group.scale.setScalar(state.appearance.height / 1.8);
```

Both lines become one:

```js
rig = buildCharacter(state.appearance);
```

and the height slider's handler (line ~595)

```js
if (rig) rig.group.scale.setScalar(state.appearance.height / 1.8);
```

becomes

```js
if (rig) rig.setAppearance(state.appearance);
```

and every other appearance control's `refresh()` should call the same thing, so
the preview shows build, skin, hair style, hair colour and marks rather than
only height. `setAppearance` re-scales the group itself, so the old
`setScalar` line is not needed anywhere.

The file header's item 2 ("`buildCharacter()` takes no appearance ... shown
nowhere") can be deleted; it is no longer true.

Optionally, to show the kit on the preview body:

```js
import { dressRig } from './gear_visuals.js';
// after the plan resolves, with the opening's starting equipment
dressRig(rig, plannedEquipment);
```

`auditAppearance(APPEARANCE)` from `player.js` throws if `openings.js` grows a
choice the rig has no look for. It is called from `gear_visuals.test.mjs`;
`creation.js` may call it at load as well if a louder failure is wanted.

## 3. `monster_models.js` (V5): what to expose for the same dressing

`dressRig` works on anything with a `parts` map. It reads anchors by name and
silently wears less on a rig that has fewer of them, which is measured: a stub
with only `handR`, `torso` and `head` dresses without throwing and puts the axe
in the right hand.

For a humanoid monster to be dressed the same way, `buildMonsterModel(id)` must
return:

```js
{
  group, parts: {
    hips, torso, head,
    armL, armR, handL, handR,     // handL/handR at the wrist, not the shoulder
    legL, legR, footL, footR,
    shinL, shinR,                 // greaves go here; without them the shins go bare
    back,
  },
  body,                           // OPTIONAL: the proportions, see below
  setAnim(name), update(dt, speedMps), dispose(),
  grip,                           // dressRig writes it; the poser should read it
}
```

`body` is the one addition beyond the polish contract. Armour is built to the
body plan, so a rig that is not the player's size should carry its own copy of
the keys it differs on:

```js
body: { SKULL_R: 0.14, TORSO_HALF: 0.30, TORSO_DEEP: 0.19,
        FOREARM_R: 0.07, THIGH_R: 0.14, SHIN_R: 0.11, ANKLE_Y: 0.16,
        HAND_Y: -0.78, HAIR_TOP: 0.34 }
```

Anything left out falls back to `BODY` from `player.js`. `dressRig` merges
`BODY`, `rig.body` and `opts.body` in that order, so a caller can also override
per call without the rig knowing.

Two things a glb rig must get right for the gear to sit:

- **The anchor frames.** `handR` must have its +y running up the forearm toward
  the elbow and its +z forward, because that is the frame `HOLD` was tuned in.
  A bone whose axis convention differs needs a fixed correction node between the
  bone and the anchor rather than a change to `HOLD`.
- **`grip`.** A skinned rig plays clips rather than writing `armL.rotation`, so
  it should map `rig.grip` to a two-handed / bow / shield additive layer or an
  alternate clip set. Until it does, a greatsword on a glb rig will hang from
  one fist. `GRIP_POSES` in `player.js` is the reference for what each grip
  name means.

Monsters that are not humanoid (spiders, wyverns, the quadrupeds) should simply
not be passed to `dressRig`. There is no need for them to carry the anchors.

## 4. Notes for whoever tunes the look

- **`HOLD` in `gear_visuals.js`** is the one table that decides how a weapon
  sits in the fist, how a shield sits on the forearm, how a bow slings across
  the back and how a sword hangs at the hip. Seven entries, each a position and
  a rotation. Every "the sword is coming out of his wrist" fix belongs there and
  nowhere else.
- **`GRIP_POSES` in `player.js`** decides where the arms go when the hands are
  holding something. Six numbers per grip, five grips.
- **`LENGTHS` in `weapon_models.js`** is the stated length of every model in
  metres, and the test holds every model to within 10% of its row. Change the
  model and the row together, or the test says so.
- **`FLAT_SHADING` in `player.js`** is `true` because `player.test.mjs` asserts
  that every mesh in the body is a flat shaded standard material, which is a
  leftover of the low poly era that the polish contract overturns. The geometry
  is already dense (sixteen sided limb sections, a lofted cranium and jaw), so
  the day that assertion is retired, flipping this one constant to `false` gives
  the body smooth normals. Weapons and armour are not affected: they were built
  smooth from the start.
- **`TEX_SIZE` in `weapon_models.js`** is 192. Fifteen texture families at three
  maps each is 6.3 MB of texel data and about 140 ms, once, when the module is
  first imported. Dropping it to 128 costs about a third of the fidelity at
  close range and saves about 80 ms of boot; raising it to 256 roughly doubles
  both.
- Textures are generated as `DataTexture`, not on a canvas, so they are
  identical in node and in the browser and the tests measure the real material.

## 5. What is measured

`node src/game/weapon_models.test.mjs` (53 checks) and
`node src/game/gear_visuals.test.mjs` (80 checks) are the record. The numbers
worth knowing:

- 32 models across weapon, shield, offhand, instrument and tool bases; `fists`
  is a deliberate `null`, and the audit knows the difference between that and a
  missing recipe.
- Every model within 10% of its stated length, worst 7.7% (spear).
- Worst model 1,496 triangles (halberd) against a 6,000 budget; 22,072 for the
  whole kit.
- Full plate plus a greatsword is 17 nodes and 5,024 triangles on the body.
- The body itself is 4,492 triangles, 33 meshes, exactly 1.8000 m tall with its
  soles at 0.0000.
- Every mesh in the kit, the body and all six armour tiers winds outward,
  checked by signed volume.
