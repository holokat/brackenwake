# W1: state.js v2, actor.js, progression.js

What Fable has to wire, what other agents may call, and every rule this agent
had to invent because `src/mmo` did not carry it.

Files owned: `src/game/state.js`, `src/game/actor.js`, `src/game/progression.js`
and their `*.test.mjs`. Nothing else was touched.

---

## 1. The create calls, in the order they go in at boot

`main.js` boots scene, state.load, runtime, hud, audio, player, camera. Three
things slot into that:

```js
// 1. as now, but load() may find a v1 save and migrate it
const state = createState();
state.load();

// 2. AFTER player is built, so the actor and the model share one position
//    object and can never be in two places
const actor = playerActor(state.character, { pos: player.pos });

// 3. AFTER floaters, hud and audio exist
const progression = createProgression({
  character: state.character,
  actor,
  floaters,          // createFloaters(sc, hudRoot)
  hud,
  audio,
  state,             // optional: progression calls state.touch() so the HUD redraws
});
```

`playerActor` needs nothing from THREE. `opts.pos` is whatever object has `x`,
`y` and `z`; passing `player.pos` (a `THREE.Vector3`) is the intended use and is
what makes floaters land over the player's head.

### The creation gate

`state.needsCreation` is true for a player who has never chosen anything and for
every player migrated from v1. `main.js` must check it before starting the
world:

```js
if (state.needsCreation) await creation.open();   // W3
```

`creation.js` finishes with `state.setCharacter(doc)`, which clears the flag and
fills the pools. Do not build the actor before creation runs, or rebuild it
after: `playerActor` reads `character.stats` by reference, but `setCharacter`
replaces the whole document, so the order is creation first, then
`playerActor(state.character, ...)`.

## 2. What runs each frame, and where

| where in the frame | call |
| --- | --- |
| after `combat.update`, before `hud.update` | `tickPools(actor, dt, inCombat)` |

`inCombat` is main.js's to decide. The suggested rule, which nothing in the
documents states: in combat if the actor swung, was swung at, or took damage in
the last 5 seconds. Health regenerates at double rate out of combat and at
single rate in it; mana and stamina do not change either way (01-STATS-SKILLS
says "out of combat x2" of health regeneration alone).

`recompute(actor)` is NOT a per frame call. It runs when something changed:

* `progression.lesson` and `progression.statLesson` call it themselves
* W3's `inventory.js` must call it after every equip, unequip and identify
* W4's abilities runtime must call it when a buff is applied or expires, and
  must set `actor.now = performance.now()` first so expired buffs drop out

`actor.equipment` is a getter onto `character.equipment`, so replacing that
object wholesale is safe.

## 3. What main.js must route

| event | call |
| --- | --- |
| a landing, `step.landed.fallMetres` from player.js | `combat.applyFall(actor, metres)` (W2). Fall damage is `combat_rules.fallDamage`, and the `fallReduction` bonus is on `actor.bonuses.fallReduction` as a fraction for whoever applies it. W1 does not apply falls. |
| every 5 s, and on unload, before `state.save()` | `syncToCharacter(actor)` |
| a lesson out of `combat.js` | `progression.applyLessons(result.lessons, 'attacker')` and again with `'defender'`, or one `progression.lesson(...)` per entry |
| chopping, in `interact.js` | `progression.lesson('lumberjacking', tree.difficulty, true)` |
| mining, in `interact.js` | `progression.lesson('mining', ore.workAt, true)` |

**`syncToCharacter` is not optional.** `actor.health`, `actor.mana`,
`actor.stamina` and `actor.pos` are the live truth during play; the document is
only written when something copies them back. Without this call a player saves
at full health however badly the fight went, and `state.setPos` is the only
thing keeping the position honest.

## 4. `window.__bw` additions

```js
window.__bw = {
  ...,
  state,             // already there; now also exposes .character, .pack, .equipment
  actor,             // the player actor
  progression,       // .lesson(id, difficulty, success), .statLesson(stat)
  spawnMonster, recompute, tickPools,   // for poking at a monster in the console
};
```

`state.character` is the live document. Reading it from the console is safe;
writing to it and then calling `state.touch()` is how a quick experiment should
be done, because a bare write does not redraw anything.

## 5. The API other agents may call

### `state.js`

Everything v1 exported still works, unchanged, as a view over the document:
`coins`, `materials`, `caps`, `goods`, `goodCaps`, `tools`, `tool`, `pos`,
`add`, `take`, `addGood`, `takeGood`, `spend`, `earn`, `giveTool`, `hasTool`,
`boughtTool`, `dev`, `setPos`, `save`, `load`, `clearSave`, `onChange`.
`interact.js` and `shop.js` were not edited and their suites are green.

New:

| name | what it is |
| --- | --- |
| `state.character` | the whole v2 document |
| `state.pack`, `state.equipment` | shortcuts into it |
| `state.needsCreation` | true until creation.js has run |
| `state.settings` | the nine settings 07 names |
| `state.touch(what)` | say that the document changed, so `onChange` fires |
| `state.setCharacter(doc)` | creation.js hands the finished character over |
| `blankCharacter()` | a whole empty v2 document |
| `hydrate(raw)`, `migrateV1(raw)` | the two load paths, exported for tests |
| `makeStack(baseId, count)` | one item record, from items.js or the local table |
| `baseOf(id)`, `weightOf(item)` | items.js first, then the local table |
| `LOCAL_BASES`, `MATERIAL_BASE`, `GOOD_BASE`, `TOOL_ITEM` | the mapping tables |
| `PACK_SLOTS` 20, `BAR_SLOTS` 12, `SKILL_IDS` | sizes |
| `auditState()` | runs at import; throws if a mapping goes stale |

### `actor.js`

`playerActor(character, opts)`, `spawnMonster(id, pos, rng)`, `recompute(actor)`,
`tickPools(actor, dt, inCombat)`, `syncToCharacter(actor)`.

Helpers worth reusing rather than rewriting: `weaponFrom(item)`,
`shieldFrom(item)`, `meditationFactor(equipment)`, `naturalWeaponFor(row)`,
`difficultyOfMonster(row)`, `applyAffix(sum, entry)`, `applyEffect(sum, effect)`,
`zeroBonuses()`, `BONUS_KEYS`, `AFFIX_EFFECT`, `FISTS`, `MONSTER_STAMINA`.

A buff is `{ id, until, effect }`. `effect` may be either

```js
{ affixes: [ affixEntry, ... ] }              // the same records gear carries
{ stats, skills, bonuses, resists, ar, pool, regen }   // a plain block
```

Set `actor.now` before `recompute` if any buff has an `until`.

### `progression.js`

`createProgression({ character, actor, floaters, hud, audio, state })`, all
optional but `character`. Returns `lesson`, `statLesson`, `applyLessons`,
`skillTotal`, `statTotal`, `lockOf`, `stats`, `resetSpoken`.

Every call returns the rule module's own result plus `said` (the lines that went
to `hud.toast`) and `floated` (the line that went over the player's head), so a
window or a test can prove a change was announced.

## 6. Rules that are missing from `src/mmo`, and what W1 did instead

`src/mmo` is finished and was not edited. Each of these is a rule the runtime
needed and could not find. They are listed so they can be moved into the pure
layer later; until then, W1's files are where they live.

### Item bases that do not exist (`state.js` `LOCAL_BASES`)

| id | why it is needed | what W1 did |
| --- | --- | --- |
| `stone` | one of the three v1 materials. 03's stack list is "ingots, ore, wood, arrows, potions, food"; stone is not in it, and Masonry needs it. | a local stack base, weight 1 |
| `pickaxe` | 07 says a migrating player's pickaxe goes in the pack. No pickaxe base exists. | a local tool base, weight 5, no slot |
| `venison`, `game_meat` | the hunting bag's two goods. A generic `food` stack would merge the deer into the rabbit. | two local stack bases, weight 0.5 |

`openings.js` names six more that `items.js` has no row for and that its own
`INVENTED_ITEM_BASES` already lists: `bandage`, `lockpick`, `reagentPouch`,
`holyBook`, `skull`, `boneStaff`, `lute`, `smithHammer`, `leatherApron`,
`darkRobe`. W3's creation.js will hit these. **Also note that openings.js and
items.js do not agree on base ids at all**: openings says `leatherChest`,
`kiteShield`, `clothRobe`; items says `leather_chest`, `kite`, `cloth_chest`.
A kit cannot be spawned through `makeItem` until somebody writes that map. W1
did not, because no kit is spawned on the migration path.

### Where an affix lands, and in what unit (`actor.js` `AFFIX_EFFECT`)

`affixes.js` gives every line a name and a size. It does not say which field of
a fighter it becomes, and `combat_rules.js` runs on two unit conventions at
once. The table in `actor.js` carries a multiplier per affix and
`auditActor()` fails at import if a new affix has no row.

Two rows are judgement rather than arithmetic:

* **Hit Chance +3 to 15%** and **Defence Chance 2 to 12%** are percent points of
  the roll. `HIT_PER_SKILL` is 0.005, so they enter as `value * 2` skill points
  and a 12% Defence Chance really is twelve points off the attacker's chance.

### Monster skills, stamina, difficulty (`actor.js`)

A monster row carries `hit` and `def` and names no skills at all.

* the natural weapon's skill comes from the note tags: `throwsKnives` gives
  Marksmanship, `swordAndShield` Swordsmanship, `casts` Magery, everything else
  Wrestling
* the actor is built so `attackSkill()` returns the row's `hit` and
  `defenceSkill()` returns its `def`, exactly, for all 48 rows (measured)
* **monsters carry 100 stamina and nothing spends it.** `combat_rules` doubles
  the swing time and takes 20 skill points off any fighter at zero stamina, so a
  monster with no stamina field would swing at half speed and ten points worse
  to hit for its whole life, in silence. This is the single largest trap in this
  wave and it is worth W2 knowing about.
* `difficulty`, the number a player learns from, is the floor of the tier band,
  and the middle of it for tier 0. That reproduces both numbers 01 quotes: a
  wraith is 70 and a critter is 5. It is not the row's `def` (the wraith's is
  75).

### The Meditation blocker (`actor.js` `meditationFactor`)

03 gives every armour tier a Meditation fraction and states the two ends, and
never says how eight pieces combine. W1 averages them over the eight armour
slots with an empty slot counting as free, so full plate is 0 and full cloth is
1, and a piece carrying the Mage Armour affix counts as free. Measured: 100
Meditation is worth 1.00 mana a second in the open and 0.00 in full plate.

### Weaknesses (`actor.js`)

`resistOf()` clamps a resist at zero, so `fireWeak`, `energyWeak`, `holyWeak`
and `silverWeak` cannot be carried as negative resists. They are on
`actor.weakTo` (a list) and `actor.vulnerability` (id to fraction, 0.25). **W2
has to apply them as a damage multiplier or they do nothing.**

### Stat locks (`progression.js`)

07 gives the document a `statLocks` map and `stats.js` has no lock rule. W1's
rule: locked or down means the stat does not rise, and says which. Nothing falls
to pay for it, unlike a skill at the 700 cap.

### A milestone sound (`progression.js` `MILESTONE_CUE`)

`audio.js` `CUES` has no sound for getting better at something. The nearest that
exists is `discover` (`upgrade.ogg`), the chime for finding a site, and that is
what plays. **Asked for: a short rising chime for a skill or stat milestone,
and a bigger one for a grandmastery.** `progression.test.mjs` asserts that
`MILESTONE_CUE` is a real row in `CUES` and that no better-named row exists yet,
so the day one is added the test says so.

### `UNARMED` and `Fists` disagree

`combat_rules.UNARMED` is 1 to 3 damage; `items.js` `WEAPONS.fists` is 1 to 4,
which is what 03 prints. The player's empty hands use `items.js`'s row (exported
as `FISTS`); monsters with no tag keep `UNARMED`'s skill id. One point of
maximum damage. Somebody should pick one.

## 7. Bonus keys that are written and read by nothing yet

The CLAUDE.md warning about twenty modifier keys nobody consumed applies here,
so the list is explicit. `actor.bonuses` carries every key an affix can produce.
`combat_rules.js` reads exactly eleven of them:

`hit`, `defence`, `dodge`, `damagePct`, `critChance`, `critDamage`,
`swingSpeed`, `armourPiercing`, `spellDamage`, `lifeLeech`, `manaLeech`.

Everything else is summed and waiting for a consumer. Exported as
`UNCONSUMED_BONUSES`:

| group | keys | who should read them |
| --- | --- | --- |
| defence | `parry`, `damageReflect`, `thorns`, `stunResist` | W2, in the resolver's caller |
| offence | `staminaLeech` | W2 |
| hit effects | `hitFireball`, `hitLightning`, `hitFrost`, `hitHarm`, `hitLifeDrain`, `hitFatigue`, `hitDispel` (each a fraction, chance per hit) | W2 |
| magic | `castSpeed`, `castRecovery`, `lowerManaCost`, `spellChanneling`, `mageArmour`, `fasterSummons`, `longerBuffs` | W4 |
| utility | `runSpeed`, `jumpHeight`, `carry`, `nightSight`, `waterWalking`, `fallReduction`, `goldFind`, `luck`, `harvestYield`, `miningSpeed`, `lumberSpeed`, `selfRepair` | player.js, interact.js, loot.js, W5 |

`carry` is the exception: it is already folded into `actor.carry` here. The
other thirty are real numbers on a real object that currently change nothing a
player can see. A tooltip promising "+15% Run Speed" is decoration until
player.js reads `actor.bonuses.runSpeed`.

## 8. Divergences from a document, on purpose

* **`heldTool` is a top level key on the document**, which 07 does not list. The
  v1 tool row is still on the HUD and `interact.js` reads `state.tool` on every
  click, so it has to survive a reload. It goes when the tool row does.
  **T3 has since taken the row off the screen.** `heldTool` is still on the
  document and still loaded, so a save written before T3 opens, but nothing
  writes it and nothing reads it to decide anything: `state.tool` is a getter
  with no setter. Which tool does a piece of work is derived from what is
  carried, by `toolFor` in `src/game/tools.js`. See
  `docs/mmo/wiring/T3-NO-TOOL-BAR.md`.
* **A fresh document keeps 120 gold**, not the 100 `openings.js` gives Blank.
  The axe is 60 and the pickaxe 80 in `shop.js`, and the whole shop suite is
  written against 120. `creation.js` overwrites the purse with the opening's own
  when it runs.
* **The 150 material cap stays** on the `add`/`materials` view. 03 says the caps
  "go away, the weight limit replaces them", and the weight limit lives in W3's
  `inventory.js`, which does not exist yet. Removing the cap now would leave the
  pack unbounded in between. The pack itself caps nothing; only the legacy view
  does. `interact.js` and `shop.js` still say "the pack is full" and mean it.
* **The v1 save is left in place until a v2 save has been written once**, then
  removed. A migrated player who never saves can still go back.

## 9. What was measured

Every number below came out of `npm test`, not out of a guess.

| claim | measurement |
| --- | --- |
| a v1 save with 37 wood migrates whole | one stack, `base: 'log'`, `count: 37`, and `state.materials.wood` reads 37 |
| the whole v1 fixture survives | 245 coins to 245 gold, 12 stone, 4 ore, 6 venison, 2 game meat, axe in mainHand, bow in ranged, pickaxe in the pack, position -212.5, 44, six of twenty pack slots used |
| v2 beats v1 | with both keys present, the v2 save loads; a corrupt v2 falls back to the v1 one rather than to nothing |
| the v1 key's life | still present after a migrating load, gone after the first `save()` |
| the 700 cap pays for itself | at 700.0 with nothing marked down the gain is refused and says so; with Alchemy marked down, 0.1 moves and Alchemy reads 99.9 |
| the climb | 0.0 to 100.0 is 1,532 successful lessons (01 says "about 1,533"), which is 77 minutes at three seconds a swing |
| 10,000 lessons at fair difficulty from 0 | 100.0 Swordsmanship from 1,532 gains, seeded rng |
| the fair chance | `gainChance(0,0)` and `gainChance(90,90)` are both 0.55; grinding rats at 90 is 0.04 |
| a refusal is not spam | 20 refused lessons produce 1 toast; changing the reason produces a second |
| monsters keep their tuned numbers | all 48 rows: `attackSkill` equals the row's `hit` and `defenceSkill` equals its `def`, worst drift 0 |
| monster stamina matters | a wolf swings every 2.20 s with stamina and 4.40 s without, and hits 59.0% against a blank character with it against 49.0% without |
| a recompute is not a heal | at 40 of 155 health, gaining +40 max health leaves 40 of 195; losing it clamps a full 195 down to 155 |
| health regen doubles out of combat | CON 50 gives 1.4 a second in a fight and 2.8 out of one; mana does not double |
| the Meditation blocker | 100 Meditation is 2.55 mana a second bare and 1.55 in full plate, so the skill's own 1.00 is exactly what the plate takes |
| a blank character | 155 health, 135 mana, 120 stamina, 140 carry |
| the warrior opening | 192.5 health, 127.5 stamina |

Suite counts: `state.test.mjs` 179 checks, `actor.test.mjs` 88,
`progression.test.mjs` 65. `interact`, `shop`, `wiring`, `hud` and `combat`
were re-run unchanged against the new state.js and are green.

## 10. Not verified

* Nothing in this wave was run in a browser. There is no `main.js` wiring yet,
  so no player has seen a floater or heard the milestone cue. Fable verifies.
* `inCombat` has no source: `tickPools` takes it as an argument and nothing
  computes it yet.
* `discovered`, `deadUntil`, `bar` and `settings` are saved and loaded and
  round trip correctly, and **nothing reads them**. `runtime.discovery` still
  keeps its own record of found sites; W5's settings window is not written; the
  bar is W4's.
* `state.settings.music` and `state.settings.sfx` duplicate what `audio.js`
  already persists under `brackenwake-audio`. Two records of the same fact.
  Whoever writes the settings window has to pick one.
