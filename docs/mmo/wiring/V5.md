## 2. The rig contract, as built from a glb

```js
rig = {
  group,                    // feet at y = 0, faces +z
  parts: {                  // fourteen anchors, always present
    hips, torso, head,
    armL, armR, handL, handR,
    legL, legR, shinL, shinR, footL, footR,
    back,
  },
  body,                     // the body plan gear_visuals sizes armour against
  grip,                     // dressRig writes it, the rig poses the arms from it
  setAnim(name), update(dt, speedMps), setAppearance(a), dispose(),
  get loaded(), get anim(), get dieDone(), ready, modelId, triangles,
}
```

### `parts.X` is not the bone, and that is the whole design

`effects.js` writes `parts.armR.rotation.x += a.armR` every frame, after the
gait, and depends on the gait having written that channel absolutely so the
addition cannot pile up. A mixer writes bones absolutely too, so the obvious
answer is "let `parts.armR` be the bone". One line kills it: `resetOwned` in
`effects.js` sets `parts.hips.rotation.x = 0` and `parts.torso.rotation.y = 0`
outright, and on a bone that throws the mixer's pose for those channels away.

So each `parts.X` is an **anchor**: an `Object3D` parented to the bone whose
`position` and `rotation` are a pure additive delta. `update` zeroes every
delta before the mixer runs, and the group's `updateMatrixWorld` (which three
calls once per render, after `effects.update`) composes them onto the bones:

```
bone.quaternion = gait * (B0inv * delta * B0)
bone.position   = gait + P0inv * deltaPos
```

`B0` is the bone's rest rotation in the character's frame. Conjugating by it is
what makes "rotation about the anchor's x" mean "pitch forward" for a bone that
points down the arm as well as for one that points up the spine. It is the same
conjugation `tools/blender/rigkit.py`'s `pose()` used to author the clips, so
the runtime layer and the baked clips agree about what forward means.

The anchor's own `updateMatrix` is overridden to emit its **rest frame** and
nothing else, so a sword parented to `handR` takes the swing once, through the
bone, and not twice. Measured: turn `armR` by 0.600 rad and the greatsword's
world rotation turns by 0.600 rad.

The rest frame is chosen so every anchor is square to the character when
nothing is moving. Measured: worst anchor 0.0000 degrees off across all
fourteen. That is the frame `HOLD` in `gear_visuals.js` and all eight armour
pieces were built in.

### Left and right are mirrored between the two rigs

A body facing +z with +y up has its anatomical right at -x, and the Blender
models are named accordingly: `upperarm_R` sits at x = -0.27. `player.js` is
not: its `armR` sits at x = +0.27. The contract says `handR` is where the
weapon goes and `buildCharacter` is the reference implementation, so this file
matches the reference and maps the contract's R onto the glb's `_L`.

Measured, both directions: the procedural `handR` is 0.060 m from the glb's
`hand_L` and 0.543 m from its `hand_R`. Mapping by name would put every weapon
in the wrong fist.

### How close the anchors sit

Bind pose, against `buildCharacter()`, in metres:

| model | worst | head | handL/R | armL/R | hips, torso, legs, shins, feet, back |
| --- | --- | --- | --- | --- | --- |
| human-slim | 0.065 | 0.030 | 0.065 | 0.032 | 0.000 |
| human-medium | 0.060 | 0.030 | 0.060 | 0.020 | 0.000 |
| human-heavy | 0.067 | 0.030 | 0.067 | 0.036 | 0.000 |

Everything is inside 0.10 m. `hips`, `torso`, `legL/R`, `shinL/R`, `footL/R`
and `back` land exactly, because `torso` and `back` are placed from the hip
bone and `BODY.BACK_Y` / `BODY.BACK_Z` rather than from a bone origin.

One number worth knowing: `effects.js` starts a bolt from the arm's matrix
times `(0, -0.62, 0)`, which is where the procedural wrist is. The glb arm is
0.540 m long, so that point lands 0.080 m below the fist. Under the 0.10 m bar,
and it will read as a spell leaving the hand rather than the fingertips.

## 3. `main.js`: the `useGlb` flag, and one call at boot

### The flag

`character.settings.glbBodies`, defaulting to true, is the natural home. Until
`win_settings.js` grows it, a constant at the top of `main.js` does:

```js
import { createGlbPlayer, preloadRigs, modelForBuild } from './rig_glb.js';
import { monsterModelIds } from './monster_models.js';

const USE_GLB = character.settings?.glbBodies !== false;
```

### Preload, before the first frame

```js
// in boot(), before startGame(). Two hundred KB of glb, nine files.
if (USE_GLB) {
  await preloadRigs([
    ...(character.appearance ? [modelForBuild(character.appearance.build)] : ['human-medium']),
    ...monsterModelIds(),
  ]);
}
```

`preloadRigs` never rejects: a file that fails to load resolves to null and
that model keeps its stand-in for the session.

**It is safe to skip the await.** Every rig returns synchronously with the
procedural body already inside it and swaps the glb in when the file lands,
keeping the same `group` and the same anchor objects, so gear that `dressRig`
already hung on a hand stays on that hand. Measured: across a swap, the group
is the same object, `parts.handR` is the same object, a child added to it is
still its child, and every anchor at rest moves at most 0.060 m. Awaiting only
buys you never seeing the swap.

### The player

Line 163 becomes:

```js
const player = USE_GLB
  ? createGlbPlayer(sc.scene, character.appearance)
  : createPlayer(sc.scene, character.appearance);
```

Nothing else changes. `createGlbPlayer` has `createPlayer`'s surface exactly
(`group`, `pos`, `parts`, `state`, `grip`, `setAppearance`, `setAnim`, `yaw`,
`speed`, `anim`, `airborne`, `landed`, `update(dt, move, heightAt)`,
`setVisible`, `teleport`, `dispose`) and runs the same controller: it imports
`stepPlayer` from `player.js` rather than copying it. `dressRig(player, ...)`,
`effects.swing(player)` and `effects.play(player, ...)` all work on it
unchanged, because they only ever reach for `parts` and `grip`.

### Nothing else

`effects.js` needs no change and must still run **after** `player.update`, for
exactly the reason it always did. `inventory.onChange` still calls `dress()`.
`monsters.js` needs no change at all: `buildMonsterModel` returns the same
contract with the same `radius`, `height`, `shape`, `parts.hit`, `anim` and
`dieDone`.

One known, small cost: `effects.handPos` calls
`parts.armR.updateWorldMatrix(true, false)`, which does not go through the
group's compose hook, so a cast light and a bolt's origin use the previous
frame's arm pose. At 60 fps that is 16 ms of lag on a point light. It was not
worth reaching into `effects.js` for.

## 4. `creation.js`: the preview body

`creation.js` takes `buildCharacter` as a dependency (line 419), so the change
is at the call site in `main.js` (line 145) and two lines inside:

```js
// main.js
createCreation(hudRoot, {
  sc,
  buildCharacter: USE_GLB
    ? (appearance) => buildGlbRig(modelForBuild(appearance?.build), { appearance })
    : buildCharacter,
  onDone: ...,
});
```

and inside `creation.js`, line 713 and line 600, exactly as V4 already asked:

```js
rig = buildCharacter(state.appearance);          // was buildCharacter(), then a setScalar
...
if (rig) rig.setAppearance(state.appearance);    // was rig.group.scale.setScalar(...)
```

`buildGlbRig`'s `setAppearance` re-scales the group itself, changes the body
when the build changes (slight, average and heavy are three different files),
retints skin and hair, and rebuilds the hair and the mark. The preview needs a
`rig.update(dt, 0)` in its render loop to breathe; without one it stands in its
bind pose, which is a stiller preview than the procedural rig's but not a
broken one.

Awaiting `preloadRigs(['human-slim', 'human-medium', 'human-heavy'])` before
opening creation is worth it there: the build slider swaps files.

## 5. What you should expect to see

- **The player** is a 312 triangle skinned body with baked idle, walk, run,
  swing, cast, hurt, die and jump clips, blended by ground speed through the
  same blend tree `models.js` already had, with the gear on top of it. A sword
  swings with the arm because it is parented under the arm's bone.
- **Locomotion crossfades**, it does not snap: idle, walk and run all play at
  once with weights continuous in speed, and the walk and run clips change rate
  with the ground so the feet do not skate. Measured: 0.035 m of ankle lift per
  stride at 7 m/s, and 21.2 degrees of shoulder swing.
- **A swing over a walk** raises the hand well clear of the walking arm and
  puts it back exactly. Measured: walking hand 0.847 to 0.918 m, with a swing
  on top 0.834 to 1.483 m, 0.565 m clear at the peak, and 0.0e+0 m of
  difference from an unswung rig forty frames after the clip ends.
- **Monsters** wearing a glb are the same size they were as boxes, to 0.0000 m.
  Nothing about the name plate, the click column or a bolt's height moves.
- **A dead monster lies down.** Measured on the skeleton: the head falls from
  1.01 m to 0.09 m and stays there, and `dieDone` still comes true at
  `DIE_SECONDS` (1.1 s) because the 1.2 s die clip is rate-scaled to fit, which
  is what keeps `CORPSE_LINGER_S` in `monsters.js` correct.
- **The tier is still in the paint.** The tier colour is multiplied over every
  material slot rather than replacing it, so a tier 5 lich is red where a tier 1
  skeleton is grey, and both keep the shading Blender baked into their vertex
  colours instead of going flat the way a box rig has to.

Triangles, counted off the buffers:

| --- | --- |
| human-slim, human-medium, human-heavy | 312 each |
| monster-skeleton | 360 |
| monster-goblin | 288 |

## 6. Which monsters are still boxes

28 of the 41 monsters above tier 0 wear a Blender body; 13 keep the box rig.
`monsterModelPlan()` prints the table and `monster_models.test.mjs` asserts it
in both directions.

| why | count | who |
| --- | --- | --- |
| its family's own model | 19 | giantRat, caveBat, skeleton, zombie, goblinScout, skeletonWarrior, goblinWarrior, giantSpider, drowned, ghoul, harpy, wraith, wyvern, boneKnight, lich, boneDragon, ashenKing, motherOfSpiders, drownedKnight |
| a stand-in body | 9 | bandit, orc, hobgoblin, cultist, mireTroll, ogre, ironGolem, werewolf, vampireKnight |
| no model for the family | 9 | thornGrub, crab, wolf, boar, bogCrawler, direWolf, stonebackBear, manticore, hydra |
| stand-in refused above tier 4 | 4 | cyclops, elderTreant, frostGiant, wardenOfTheCut |

- **`wolf` and `grub` have no glb at all.** Four legged animals and the low
  crawling things. They keep the box rig until something is built for them.
- **`biped` has no model of its own** and borrows `human-heavy`. A bandit or an
  orc reads as a big man and that is fine. A cyclops, a frost giant, an elder
  treant or the Warden of the Cut does not: a 4 m human is a lie about what you
  are fighting. `STANDIN_MAX_TIER` is 4, so above tier 4 a biped keeps the box
  silhouette, and **no boss wears a stand-in body**. The three bosses that do
  wear a glb (ashenKing, motherOfSpiders, drownedKnight) wear their own
  family's.
- **`flyer` is a bat** for the cave bat, the harpy, the wyvern and the bone
  dragon. That is the family's own model rather than a borrowed one, but a bat
  scaled to 3.4 m is still a bat: a wyvern will read as a very large bat until
  something better is built. Worth a row of its own in whoever's queue owns the
  Blender files.

Scaling: `src/mmo/monsters.js` carries no size field, so the size is what it
always was, `TIER_HEIGHT` nudged by hit points within the tier. The box rig is
built first in every case, its silhouette is measured with a `Box3`, and the
glb is scaled to match it. That is why `radius` and `height` are untouched.

## 7. What is approximated, and what is not verified

**Approximated, deliberately:**

- **Hair styles.** Each glb carries one baked head of hair in a `hair` material
  slot. The twelve styles `openings.js` offers are not modelled. What a style
  gets is the baked hair tinted to the chosen colour, plus a tinted cap and,
  where the silhouette needs one, a braid, a pair of braids, a ponytail, a bun,
  a bob, a fall or five tufts, built in code by `hairCap`. `shaved` hides the
  baked mesh and adds nothing. Every one of the twelve builds something or is
  deliberately bare, and the test holds that. What it is not is twelve distinct
  cuts: `cropped`, `short`, `swept` and `tousled` differ only by the cap, which
  is to say they differ hardly at all.
- **Face marks.** The brief said a decal on the face material. These models
  ship with no textures at all and `tools/validate-glb.mjs` holds them to that,
  so a real decal would mean a texture, a UV set and a new check. What
  `markDecal` builds instead is what `player.js` builds: a small coloured quad
  standing a millimetre off the face, positioned from the `MARKS` table, shifted
  down 0.030 m because the glb head bone sits that much above the procedural
  head's origin. It reads the same at any distance a player sees it from and it
  is not a decal.
- **Grip.** `GRIP_POSES` is applied into the additive layer as part of the gait,
  so a greatsword closes both hands the way it does on the procedural rig,
  rather than through a separate additive clip set. There is no baked
  two-handed or bow clip to blend to.
- **Non-humanoid anchors.** The rat, the spider and the bat resolve all fourteen
  anchors, but several of them share a bone (a rat's `legL`, `shinL` and `footL`
  are all `legB_R`) because those bodies have nothing else to offer. They are
  present so `dressRig` cannot throw, not because anything should dress a bat.
  `isHumanoid(id)` says which models have real arms and legs.

**Not verified:**

- **Nothing has been looked at.** There is no browser in this seat. Every claim
  above is a number out of a node test driving the real loader over the real
  files, and none of it is a claim about how the body reads on screen. Whether
  the swing looks like a swing, whether the tier wash is too dark on a tier 6,
  and whether a wyvern that is a large bat is acceptable are all for Fable to
  look at.
- **`main.js` and `creation.js` are not wired.** Section 3 and section 4 are
  instructions, not diffs. Until someone applies them the player is still the
  procedural body and only monsters are on Blender rigs.
- **Performance.** Forty skinned monsters each with their own `AnimationMixer`
  has not been profiled. The triangle counts are tiny; the mixer cost is not
  measured.
- **The compose hook fires on `updateMatrixWorld`.** In the running game that is
  once per render, from `WebGLRenderer.render`. A second renderer, a
  render-to-texture pass or a manual `scene.updateMatrixWorld()` between the
  gait and the render would compose more than once, which is harmless because
  the composition always starts from the stored gait pose rather than from the
  bone's current value, but that idempotence is asserted only in node.
