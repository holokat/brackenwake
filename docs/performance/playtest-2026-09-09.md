# Brackenwake performance fixes, 9 September 2026

Implemented and verified locally in `/Users/k/brackenwake`. Production release is
pending the committed-source build and deployment checks.
The full route completed with loaded artwork, no failed rooms, no WebGL errors,
and no visibility interruptions. A final targeted entry/walk/orbit run verified
the last correction to shader preparation.

## Results

The detailed entrance improved from 24.67 FPS to 60.06 FPS in the measured idle
segments. The nave orbit improved from 29.15 FPS to 60.06 FPS. This includes
adaptive 3D resolution: the original runs used a fixed 1.5 pixel ratio; the full
optimized route used roughly 0.95 to 1.35. HUD rendering is independent of that
adjustment. These results are not a claim of identical pixel counts or universal
60 FPS on every device.

The combat segment used the real attack system: Oram Blackhand's health changed
from 780 to 582 during 15 seconds. All 24 dungeon creatures had finished spawning
by the sampled endpoints, with no outstanding work-queue jobs.

The final shader correction was verified in a separate fresh-page run. Corridor
walking recorded 57.05 FPS, 20.3 ms p95 and an 86.4 ms worst frame. Its nave orbit
recorded 60.02 FPS, 17.6 ms p95 and a 29.4 ms worst frame, ending at pixel ratio
1.4. Entry still had a 178.1 ms outlier. The full route table above predates only
that last correction; it has not been silently substituted with a different run.

## What changed

| Before | After |
| --- | --- |
| Fixed 3D resolution during sustained slow frames | A bounded controller reduces pixel density after two slow measurement windows and recovers gradually. The selected setting is the ceiling; text and controls remain at their normal resolution. |
| Full-resolution bloom emission and blur | Half-resolution glow buffers, with the existing full-scene occlusion, colour conversion, antialiasing and spell distortion paths preserved. |
| Room shaders warmed with hidden entrance lights and sometimes the wrong output target | Warm-up includes the final room lights and both plain and HDR output variants. Existing visible material variants are prepared without cloning circular gameplay state. Non-glowing rooms also prepare HDR shaders when ambient effects use the composer. |
| Four static cube shadow maps initialized together on artwork reveal | One shadow map is prepared per queued job before attachment. Cancellation frees partial maps; completed maps belong to the room's existing lights. |
| Magical fixtures across the floor each adding lights and particle updates | A stable pool of at most three magic lights follows nearby fixtures. Distant fixture animation is skipped. |
| A teleport constructing the entire selected creature roster synchronously | Nearby creatures remain immediate. Distant creation uses the shared queue, with promotion on approach and cancellation on roster changes, death or disposal. |
| Shared stone sheets first prepared on dungeon entry | Two common stone families and their textures are prepared under the initial boot cover. |
| No reproducible route with frame/system attribution | A separate production-build profiler records real frames, system CPU time, browser long tasks, renderer resources, loading queues and transition stages. |

The existing spatial room stream still controls detail residency and stair-asset
prefetching. No complete future dungeon artwork set is loaded by these changes.
Existing dungeon-builder commits are preserved. Uncommitted authored island edits
and lore work are excluded from this performance change and its game release.

## Transition work

Timing the actual synchronous operations exposed the creature-creation cost.
Before the distant-spawn queue, first-entry arrival listeners cost 172.3 ms.
Afterward, the measured first-entry listener work was 7.1 ms.

| Synchronous operation | Before creature queue | After |
| --- | ---: | ---: |
| Enter dungeon | 299.2 ms | 141.7 ms |
| Descend to floor two | 192.1 ms | 93.5 ms |
| Return upstairs | 194.8 ms | 120.2 ms |
| Leave dungeon | 427.2 ms | 72.6 ms |

These are operation durations, not whole-frame durations. A subsequent render can
add a separate stall. The earlier column already includes the first rendering
fixes, so it isolates a later stage of the work rather than pretending to be the
original baseline.

## Remaining hotspots and limits

This is a measured improvement, not a claim that every performance issue is fixed.
Basic floor construction is still synchronous. In the full route's first entry,
layout/disposal took 16.7 ms, basic scene creation 72.9 ms and furnishings 43.9 ms.
Preparing and consuming a cancellable basic floor shell ahead of a stair remains
a follow-up. The original aspiration to remove all transition frames above
100 ms has not been met. Occasional first-use and resolution-change stalls also
remain, and returning to the surface is heavier than steady dungeon play.

Memory and queues were checked across entry, walking, combat, floor changes and
return. Detailed room residents remained at one or two at the sampled endpoints,
and queues emptied. Heap collection was observed, including a drop from about
658 MiB to 428 MiB between segments; the final surface sample was about 621 MiB.
These short runs do not establish a leak-free long-session plateau. A longer
repeat-route soak is still needed before making that claim.

## Measurement method and evidence

Apple M2 Max Mac Studio, 64 GB physical memory, existing Brave Chromium 151
session using ANGLE Metal. Viewport: 2560 by 1235 CSS pixels. The original draw
buffer was 3840 by 1852 at pixel ratio 1.5. No network throttling; assets served
locally. Existing browser tabs were preserved. Heavy local tests/builds were
stopped during measurement.

The profiler imports the actual game and uses real animation frames in solo
mode. A temporary character and memory-only storage protect player saves. Its
survival assistance restores player health without changing monster AI or attack
execution. Multiplayer, production-network latency, other hardware and long
session memory retention were not measured.

GPU timer queries are recorded diagnostically, with asynchronous polling and
rejection of disjoint results. They are not used as GPU utilization percentages
or as substitutes for observed frame intervals. Probe version 1 overcounted
cumulative draw statistics after postprocessing disabled renderer auto-reset;
its draw/triangle figures are excluded. Frame and CPU timing were unaffected.
Version 2 records per-render counter deltas. Failed development runs are excluded.
